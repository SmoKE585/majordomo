# deploy.sh — обновление системы из терминала

`deploy.sh` в корне проекта делает то же, что кнопка «Обновить систему» в
панели, но по SSH и без веб-сессии. Он нужен, когда панель отвечает медленно,
обрыв связи рвёт HTTP-запрос обновления или нужно обновиться с сервера, где
браузер неудобен.

Скрипт — только оформление и запуск. Само обновление выполняет команда
`php majordomo deploy:update` (`lib/core/Deploy/SystemUpdate.php`), поэтому
веб-обновление и `deploy.sh` оставляют одинаковые файлы состояния и одинаково
заменяют файлы.

```
deploy.sh  →  php majordomo deploy:update  →  lib/core/Deploy/SystemUpdate.php
```

## Требования

- Linux, bash 4+, CLI PHP **той же версии**, что PHP-FPM (8.1+);
- `tar`, Composer, Node.js 24+ и npm (если `DEPLOY_ASSETS` не `never`);
- `mysqldump` (или `PATH_TO_MYSQLDUMP` в `.env`);
- пользователь проекта — владелец файлов; запуск от `root` нежелателен.

Проверить готовность, ничего не меняя:

```bash
./deploy.sh --check
```

Если файл не исполняемый (например, после копирования по FTP):

```bash
chmod +x deploy.sh
# либо без права запуска:
bash deploy.sh --check
```

## Быстрый старт

```bash
cd /var/www/.../majordomo

./deploy.sh --plan     # какой коммит будет установлен
./deploy.sh --check    # проверки окружения, без изменений
./deploy.sh            # проверки → подтверждение → обновление
```

Для автоматизации (cron, CI) — без интерактивного подтверждения:

```bash
./deploy.sh --yes
```

## Что происходит по шагам

| Шаг | Что делает | При ошибке |
| --- | --- | --- |
| 1. Проверка окружения | PHP, cURL, `tar`, `mysqldump`, Composer, Node.js, npm, права на каталоги, свободное место, wrapper службы | обновление не начинается, файлы не тронуты |
| 2. Источник и версия | читает Atom-ленту `GIT_URL`, берёт последний коммит, строит ссылку на архив **этого коммита** | обновление не начинается |
| 3. Резервная копия базы | `mysqldump` в `cms/saverestore/db_before_update_<дата>.sql` | обновление не начинается (`--skip-backup` отключает шаг) |
| 4. Скачивание | архив в `cms/saverestore/master.tgz`, проверка размера и SHA-1 | обновление не начинается |
| 5. Распаковка | `cms/saverestore/temp`, поиск корня проекта, проверка прав на каждый файл | обновление не начинается |
| 6. Остановка | режим обслуживания `cms/maintenance.json`, пауза циклов через `cms/cycles` | пауза снимается, сайт возвращается |
| 7. Замена файлов | `deploy/removals.json`, удаление исчезнувших файлов, копирование по манифесту | сайт остаётся в режиме обслуживания, циклы удерживаются |
| 8. Зависимости | `composer install`, проверка автозагрузки, сборка фронтенда, `migrations:run` | то же: режим обслуживания и удержание циклов |
| 9. Перезапуск | `systemctl restart` через wrapper (`DEPLOY_RESTART=1`) | версия не фиксируется, сайт остаётся в обслуживании |
| 10. Завершение | состояние деплоя, снятие режима обслуживания, очистка `temp` | — |

Чего обновление **не делает**:

- не создаёт файловых бэкапов (сохраняется только база) — это решение проекта;
- не трогает `cms/`, `.env`, `config.php`, `vendor/`, `node_modules/`, `.git/`,
  `backup/`, `database_backup/` и пользовательские модули;
- не обновляет модули из «Маркета дополнений» — это отдельная операция.

## Версия в панели

После успешного обновления версия фиксируется не сразу: скрипт оставляет
`cms/saverestore/update.pending.json` со статусом `applied`. Панель при первом
открытии (дашборд или «Обновление системы») вызывает `reconcilePendingUpdate()`
и записывает коммит в конфиг модуля — это тот же механизм, который спасает
веб-обновление при обрыве запроса во время перезапуска службы.

Поэтому после `deploy.sh` откройте панель один раз: в карточке версии появится
установленный коммит, а «есть обновление» исчезнет.

## Опции

| Опция | Действие |
| --- | --- |
| `--check` | только проверки окружения |
| `--plan` | показать установленный и доступный коммит, ссылку на архив |
| `--yes`, `-y` | без подтверждения |
| `--url=URL` | другой архив (важнее `.env`) |
| `--branch=ВЕТКА` | `master`, `alpha` или другая ветка |
| `--skip-backup` | без дампа базы (не рекомендуется) |
| `--no-restart` | обновить файлы, службу перезапустить вручную |
| `--keep-temp` | оставить `master.tgz` и распакованный архив для разбора |
| `--insecure` | не проверять TLS-сертификат |
| `--force` | обновить, даже если этот коммит уже установлен |
| `--allow-root` | не перезапускать скрипт от пользователя проекта |

Источник берётся из `.env` (`GIT_URL`, при необходимости `MASTER_UPDATE_URL`).
Выбор ветки в панели (`alpha`/`master`) хранится в конфиге модуля и на CLI не
влияет: для другой ветки передайте `--branch=alpha` или `--url=...`.

Если запустить скрипт через `sudo`, он сам перезапустится от пользователя
проекта: иначе новые файлы получили бы владельца `root`, и служба потеряла бы
права на запись. Отключить это поведение — `--allow-root`.

## Журнал и ошибки

Каждый запуск пишет журнал в `cms/deploy/deploy-<дата>-<время>.log` (вывод
`deploy:update` без цветовых кодов). При ошибке скрипт показывает последние
строки журнала и команду для повтора.

Что делать в типовых случаях:

- **Нет прав на запись** — файлы принадлежат другому пользователю. Выровняйте
  владельца с пользователем службы: `sudo chown -R <user>:<group> <проект>`.
- **Нет Composer / Node.js / npm** — установите инструменты или задайте
  `DEPLOY_COMPOSER`, `DEPLOY_NODE`, `DEPLOY_NPM` в `.env`; для сервера без
  сборки фронтенда допустимо `DEPLOY_ASSETS=never` (используется готовый бандл).
- **Циклы не подтвердили остановку** — скрипт завершится ошибкой до замены
  файлов. Перезапустите службу и повторите: `sudo systemctl restart majordomo-<user>`.
- **Служба не перезапустилась** — файлы уже обновлены. Проверьте
  `systemctl status`, исправьте причину, затем `php majordomo migrations:run`
  и `php majordomo maintenance:off`.
- **«Уже выполняется другое обновление»** — держится блокировка
  `cms/deploy/update.lock`. Дождитесь завершения второго процесса; после
  аварийного обрыва блокировка снимается сама (flock живёт вместе с процессом).
- **Сайт остался на 503** — снимите режим вручную: `php majordomo maintenance:off`
  (он же снимает `cms/cycles/deploy.hold`).

## Ручной запуск без обёртки

`deploy.sh` не обязателен — команда самодостаточна:

```bash
php majordomo deploy:update --check
php majordomo deploy:update --plan
php majordomo deploy:update --yes
php majordomo deploy:update --yes --json      # машинный вывод
```

`--json` возвращает `{ok, data, messages, error}`; `data` содержит `from`, `to`,
`branch`, `archive_url`, `archive_sha1`, `backup`, `files`.

## Коды выхода

| Код | Значение |
| --- | --- |
| 0 | обновление выполнено (или уже была последняя версия) |
| 1 | обновление не выполнено; смотрите журнал |
| 2 | ошибка запуска: не тот каталог, нет PHP, неизвестная опция |
| 3 | отменено пользователем |
