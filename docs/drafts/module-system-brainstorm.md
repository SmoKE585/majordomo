# Фантазии о развитии модульной системы

> **СТОП ДЛЯ АГЕНТОВ. Это только фантазии и черновик для обсуждения с владельцем,
> а не утверждённая архитектура, спецификация, инструкция или план внедрения.
> Агентам нельзя никак использовать этот файл при выполнении других задач:
> ориентироваться на него, принимать по нему решения, ссылаться на него как на
> правило, менять код, переносить файлы, устанавливать зависимости или начинать
> миграцию. Сам факт наличия файла ничего не разрешает. Обсуждать или редактировать
> сам черновик можно только по отдельному прямому поручению владельца.
> Действующие правила проекта и фактический код остаются источником требований.**

Дата обсуждения: 2026-10-23. Ни один из описанных ниже новых механизмов этим
документом не вводится. Названия каталогов, полей и будущих API условные.

## 1. Замысел

Хочется доработать существующую систему так, чтобы модуль был самодостаточным
пакетом: его можно установить, обновить, отключить и полностью удалить через
один менеджер. Логика конкретного устройства или сервиса остаётся внутри модуля.
Ядро предоставляет общие инструменты и управляет жизненным циклом.

Самодостаточность означает, что пакет содержит собственный код и описание всех
требований. Общие библиотеки при этом могут предоставляться системой: отдельная
копия Alpine, Bootstrap или PHP-библиотеки каждому модулю не нужна.

Системные сущности MajorDoMo — **классы, объекты, свойства и методы**.
Общую сущность «устройство» этот замысел не вводит. Устройства и подключения
Keenetic, станции Yandex Devices, команды Tuya — собственные данные соответствующих
модулей. Модуль определяет их смысл и связывает их с объектами и свойствами
системы. Ядру для обслуживания связи достаточно знать владельца, стабильный
ключ источника и целевое свойство; протокол и модель оборудования ему не нужны.

## 2. На что опираемся сейчас

Это наблюдения по коду на дату обсуждения, а не новый контракт:

- `lib/module.class.php`: базовый `module`, `checkInstalled()`, `install()`,
  `uninstall()`, `dbInstall()`, настройки в `project_modules` и маркер установки.
  Проверка установки может вызываться из конструктора модуля.
- `modules/market/market.class.php`: распаковка, импорт, копирование файлов,
  вызов удаления модуля, удаление каталогов и файлов по списку `.files`.
- `modules/control_modules/control_modules.class.php`: переустановка модулей
  через снятие маркеров и создание экземпляров, затем миграции ядра.
- `lib/core/Migrations.php`: файловые миграции ядра с журналом и блокировкой.
  Это пока не универсальный механизм миграций модулей.
- `resources/js/modules/admin_panel/115_alpine.js`: общий экземпляр Alpine
  экспортирован в `window.Alpine`; запуск и обработка нового дерева при
  `partLoad` уже находятся в оболочке.
- `composer.json`: совместимость с PHP 8.1, общая автозагрузка ядра.
  `package.json`: локальная сборка Vite, Alpine 3 и Bootstrap 5.

Сейчас ответственность за установку и очистку распределена. Список файлов
не описывает таблицы, привязки, задания, подписки и остальные созданные ресурсы.

## 3. Возможная структура самодостаточного пакета

```text
modules/example/
├── module.json                  # паспорт модуля и точки подключения
├── example.class.php            # совместимый вход на базе module
├── composer.json                # PHP-пакеты и автозагрузка кода модуля
├── package.json                 # npm-пакеты и требования к общему UI
├── package-lock.json            # воспроизводимая сборка собственных ассетов
├── src/                         # логика модуля
├── migrations/                  # последовательные изменения собственных данных
├── lifecycle/                   # особые действия установки/удаления, если нужны
├── templates/admin/             # шаблоны админки
├── resources/js/                # исходники интерфейса
├── resources/css/               # исходники стилей
├── assets/                      # готовые браузерные файлы и иконка
├── docs/                        # документация модуля
└── tests/                       # изолированные проверки
```

Пустые каталоги и файлы без практической необходимости не нужны. Простой модуль
может состоять из паспорта, класса, шаблона и иконки.

Исходный пакет хранится целиком в своём каталоге. Браузерные файлы менеджер
публикует только в `public/assets/modules/example/`, с учётом владельца и версии.
Прямой HTTP-доступ к PHP-коду, миграциям и настройкам пакета не нужен.
Изменяемые данные, кеш и временные файлы получают отдельное место вне исходников
и публичного каталога. Точный путь пока не выбран.

Новая раскладка шаблонов потребует поддержки загрузчиком. Старые расположения
`templates/<name>/`, циклы и URL продолжают работать через совместимость;
этот эскиз сам по себе ничего не переносит.

## 4. Паспорт модуля

Возможный состав `module.json`:

| Блок | Что в нём описывается |
| --- | --- |
| Идентичность | Стабильный идентификатор, название, версия, описание, автор |
| Совместимость | Версия формата паспорта, требования к ядру, PHP и расширениям |
| Зависимости | Другие модули, необходимые возможности ядра и диапазоны версий |
| Точки входа | Класс модуля, каталог миграций, особые действия жизненного цикла |
| Админка | Иконка, меню, маршруты, шаблоны и входные файлы ассетов |
| Фон | Циклы, расписания, обработчики очереди и событий |
| Данные | Собственные ресурсы и правила работы со связанными объектами |
| Настройки | Схема, значения по умолчанию и признаки секретных полей |

Composer- и npm-требования живут в стандартных файлах, а не дублируются в
паспорте. Менеджер читает их вместе с паспортом и проверяет согласованность.
Модуль не меняет меню, таблицу маршрутов и конфигурационные файлы ядра вручную.

## 5. Менеджер и базовый класс

Один общий менеджер обслуживает маркет, ручную установку и будущие команды
`php majordomo`. Маркет выбирает пакет и показывает результат, но не содержит
вторую реализацию установки.

Менеджер отвечает за проверку требований, зависимости, блокировки, миграции,
регистрацию ресурсов, публикацию ассетов, запуск и остановку фоновой работы,
прогресс и восстановление после ошибки.

Базовый класс остаётся тонкой точкой подключения к системе. Модуль получает
готовые инструменты и при необходимости определяет особые действия установки
и удаления. Общие операции не приходится копировать в каждый `uninstall()`.

Возможное направление для нового формата: создание экземпляра и открытие
страницы ничего не устанавливают, не меняют схему и не запускают пакетные
менеджеры. Установка и обновление происходят явно через менеджер. Это изменение
текущего жизненного цикла, поэтому старому формату нужен отдельный совместимый
режим без двойного вызова `install()` и миграций.

Установка чужого PHP-кода остаётся установкой доверенного расширения. Учёт
владения ресурсами не превращает произвольный PHP в изолированную среду и не
позволяет автоматически найти все последствия обхода общих инструментов.

## 6. Composer-зависимости

Желаемый сценарий: автор описывает PHP-пакет и допустимую версию в
`composer.json` модуля; менеджер при установке подбирает и загружает совместимые
версии, после чего модуль использует обычную автозагрузку.

Предлагаемая модель — единый согласованный набор PHP-зависимостей ядра и всех
установленных модулей. Отдельные `vendor` у модулей не гарантируют совместимость
одноимённых классов в одном PHP-процессе.

### Как это могло бы выглядеть для автора и менеджера

Автор добавляет обычные `require` и `autoload` в `composer.json` своего модуля.
Устанавливать библиотеку собственным `install.php`, подключать её файлы вручную
или менять `composer.json` ядра ему не требуется. После успешной установки
классы пакета доступны обычным способом через общую автозагрузку.

Предлагаемый путь — служебный Composer-проект конкретной установки:

1. Менеджер формирует его корневой манифест из требований и автозагрузки ядра
   и списка выбранных версий модулей. Исходные манифесты ядра и модулей
   остаются под управлением своих авторов.
2. Модули с PHP-зависимостями подключаются как локальные Composer-пакеты
   через управляемые `path`-репозитории. Менеджер задаёт их имена, версии и
   проверенные пути; код оригинального пакета продолжает принадлежать модулю.
3. Требования каждого модуля поступают решателю Composer как отдельные
   требования пакета. Склеивать массивы `require` с перезаписью одинаковых
   ключей нельзя: так потеряются ограничения одного из потребителей.
4. Composer подбирает совместимый граф и записывает общий `composer.lock`.
   Lock отдельного модуля может служить его разработчику для тестов, но
   не задаёт версии всей установленной системы.
5. Менеджер готовит полный набор библиотек и автозагрузку в отдельной области,
   проверяет его и согласованно активирует. Приложение использует одну
   выбранную общую автозагрузку без параллельного подключения старых копий.

`Path`-репозитории — существующая возможность
[Composer](https://getcomposer.org/doc/05-repositories.md#path).
Дополнительные репозитории должны попадать в управляемый корневой манифест:
Composer не наследует `repositories` из зависимых пакетов. Список разрешённых
источников контролирует менеджер, а не произвольный модуль.

Например, модулям нужны версии одной библиотеки `^2.0` и `^2.4`: Composer может
выбрать подходящую обоим версию 2.x. Если новый модуль требует `^3.0`, а первый
остаётся на `^2.0`, установка останавливается с объяснением конфликта.
Автоматическая загрузка двух несовместимых версий с одинаковыми именами классов
в один процесс не предлагается.

Текущий lock-файл служит отправной точкой для минимального изменения графа.
Установка модуля не разрешает заодно произвольное обновление библиотек ядра;
необходимое изменение их версий требует отдельного согласованного обновления.
Установленные, но отключённые модули пока также участвуют в расчёте требований.
Восстановление установки выполняется по общему lock-файлу, без нового выбора
«самых свежих» версий на каждом запуске.

Идеи для механизма:

- собрать требования ядра, установленных модулей и кандидата в общий расчёт;
- учитывать диапазоны всех потребителей, включая транзитивные зависимости;
- сохранить точные выбранные версии в общем lock-файле установки;
- при конфликте показать пакет, требования и потребителей и остановиться до
  изменения рабочей установки; несовместимую версию молча не подставлять;
- подготовить зависимости и автозагрузку отдельно от работающего `vendor`;
- проверить реальные требования платформы; PHP 8.4 на машине разработчика
  не отменяет заявленную совместимость нового кода с PHP 8.1;
- активировать согласованный набор вместе с кодом модуля и перезапустить
  долгоживущие процессы, которые используют прежнюю автозагрузку;
- не выполнять без необходимости полное обновление пакетов остальных модулей.

Место служебного манифеста и `vendor`, перенос относительных путей ядра,
автозагрузка из стабильных путей после подготовки и согласование с системным
деплоем ещё требуют решения. Служебная область не должна быть доступна по HTTP.
Переход с существующего `vendor` — отдельная работа над загрузчиком и деплоем;
одной установки Composer внутри каталога модуля для этого недостаточно.

После удаления модуля пересчитывается граф требований. Пакет удаляется, только
если он больше не нужен ядру, другому модулю или оставшейся транзитивной цепочке.
Пакеты других потребителей не являются мусором удаляемого модуля.

Composer запускается контролируемым исполнителем менеджера, с явными путями и
аргументами. Выполнение произвольных Composer scripts и plugins не включается
автоматически: для необходимых исключений потребуется отдельная политика.
Пароли приватных репозиториев не хранятся в паспорте и журнале операции.

Это согласуется с различием между разрешением новых требований и установкой
точных версий из lock-файла в [документации Composer](https://getcomposer.org/doc/03-cli.md#install-i).
Восстановление файла lock само по себе не восстанавливает содержимое `vendor`.

## 7. npm-зависимости и сборка

Желаемый сценарий аналогичный: модуль описывает зависимости в `package.json`,
менеджер получает пакеты локально, собирает собственные JS/CSS модуля и
публикует готовые файлы. CDN не требуется.

В отличие от PHP, собственные браузерные библиотеки можно включать в отдельный
бандл модуля. Начальный вариант для обсуждения — отдельная сборка каждого модуля
со своим lock-файлом, а не добавление всех библиотек в общий `admin.js`.
Система даёт общий сборочный инструмент; модулю не нужно копировать весь Vite
проекта. Версии инструмента сборки тоже должны быть воспроизводимыми.

### Как это могло бы выглядеть для автора и менеджера

Автор добавляет собственную библиотеку в `dependencies`, пишет обычный импорт
в исходном JS и задаёт входные файлы модуля. Общий сборочный инструмент знает,
как получить из них готовые JS/CSS. Произвольная конфигурация сборки для простого
модуля не обязательна.

Менеджер копирует выбранную версию в служебный каталог сборки, устанавливает
пакеты по `package-lock.json`, выполняет стандартную сборку и проверяет результат.
Только готовые браузерные файлы публикуются в `public/assets/modules/<name>/`.
Браузер не получает доступ к `node_modules`; исходный `package.json` ядра
при установке модуля не меняется.

Разные модули могут использовать разные версии собственной библиотеки, если
она допускает независимую работу и включается в их отдельные бандлы. Для
библиотек, меняющих глобальное состояние или требующих общего экземпляра,
нужна явная проверка совместимости. Общую дедупликацию всех npm-пакетов
между модулями можно отложить: отдельная сборка проще для первого варианта.

Область сборки со своим `node_modules` можно удалить после успешной публикации;
для работы страницы нужны готовые ассеты. Менеджер учитывает и удаляет прежние
файлы публикации, когда они больше не используются, и всю публикацию при
удалении модуля. Это не требует пересборки общего интерфейса ядра.

Пакет, выпущенный автором, уже содержит lock-файл для своей сборки. Если менеджер
его генерирует, это отдельный этап разрешения зависимостей с фиксацией результата.
`npm ci` используется только для согласованного lock-файла и в подготовленном
каталоге: команда не добавляет новые требования и может заменить имеющийся
`node_modules`. См. [документацию npm](https://docs.npmjs.com/cli/v11/commands/npm-ci/).

Обычные зависимости собираются вместе с модулем. Общие рантаймы оболочки
заявляются как требования к предоставляемому системой API, а не включаются
повторно. Для npm это можно выразить через `peerDependencies`, но одного этого
поля недостаточно: сборщик должен исключать общую библиотеку из бандла и
связывать импорт с экземпляром оболочки.

В частности, `peerDependencies` само по себе не гарантирует отсутствия второй
копии Alpine: npm умеет устанавливать peer-пакеты. Общий сборщик должен
перенаправлять такой импорт на адаптер общего `window.Alpine`, а менеджер —
проверять диапазон версии, которую предоставляет оболочка. Разработка и сборка
могут использовать локальный пакет для проверки, но его рантайм не попадает
в бандл модуля. См. описание
[peerDependencies в npm](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#peerdependencies).

Ассеты загружаются только на страницах модуля, с версией или хешем для кеша.
Удаление убирает его опубликованные файлы, собственную область сборки и данные.
Общие пакеты и кеши, которые нужны оставшимся потребителям, сохраняются.

Установочные scripts зависимостей по умолчанию отключены. Если сборочный
инструмент без них не работает, нужно заранее определить разрешённые шаги;
молчаливый повтор установки с разрешением всех scripts не подходит.
При отсутствии нужных инструментов установка завершается понятной ошибкой до
активации. Готовая сборка автора — возможный отдельный вариант поставки,
но политика её проверки пока не выбрана.

## 8. Общий UI, маршруты и публичные входы

### 8.1. Один Alpine для оболочки и модулей

Делиться Alpine уже есть чем: оболочка предоставляет `window.Alpine`.
Предлагается развить это в явный контракт возможностей UI:

- один экземпляр Alpine и один вызов `Alpine.start()` со стороны оболочки;
- модуль получает этот экземпляр, регистрирует собственные именованные
  компоненты и использует обычные `x-data`, `x-show`, `x-on` и другие директивы;
- имена компонентов и хранилищ имеют префикс модуля, чтобы избежать конфликтов;
- загрузчик сначала получает JS модуля и регистрирует его компоненты, затем
  разрешает Alpine обработать его разметку — и при первом открытии, и при
  `partLoad`; существующего наличия глобала для такого порядка недостаточно;
- события регистрации не должны теряться, если общий Alpine уже запущен;
- переход со страницы освобождает обработчики, таймеры, наблюдатели и подписки
  модуля; повторный переход не дублирует их;
- плагины, меняющие общий Alpine, требуют отдельного согласования совместимости
  и порядка запуска. Произвольная поздняя регистрация всех плагинов не обещается.

Требования к порядку расширения общего экземпляра описаны в
[документации Alpine](https://alpinejs.dev/advanced/extending).
Для Bootstrap, компонентов `MDJUI`, редактора и других общих возможностей
нужен похожий принцип: модуль запрашивает возможность и совместимость, а не
подключает собственную копию всей оболочки.

### 8.2. Генерация URL и путей

При установке менеджер регистрирует именованные маршруты из описания модуля.
Главная страница получает адрес по идентификатору модуля, остальные страницы
описываются относительным путём и разрешённым обработчиком. Одно описание
используется для разбора входящего запроса и построения исходящей ссылки.
Править таблицу маршрутов ядра для каждого нового модуля не требуется.

Условные примеры будущего API:

```php
$this->url('index');
// /panel/keenetic.html

$this->url('settings');
// /panel/keenetic/settings.html

$this->url('router.edit', ['id' => 12]);
// /panel/keenetic/routers/12.html

$this->asset('main.js');
// URL опубликованного ассета с версией или хешем

$this->path('templates/admin.php');
// файловый путь внутри пакета

$this->dataPath('cache/state.json');
// файловый путь внутри области данных модуля
```

Генератор учитывает префикс установки, кодирует параметры и проверяет
обязательные значения. Файловый путь и URL — разные операции; произвольные
выходы за границы пакета и области данных не разрешаются.
PHP-шаблоны получают тот же контекст. JS получает готовые адреса действий
через конфигурацию страницы или `data-url`, без вычисления относительно
текущего URL при `partLoad`.

Маршрут задаёт HTTP-метод и конкретный разрешённый обработчик. Изменение данных
проходит проверку прав и CSRF; произвольный метод класса не публикуется.
Существующие URL, `parseLinks()` и legacy-состояние сохраняются через
совместимость. При отключении и удалении регистрации модуля отзываются.

### 8.3. Модуль сам публикует свои webhook и управляет ими

Пожелание владельца: пользователю достаточно настройки в самом модуле.
Создавать вход вручную в разделе API, выбирать файл и переносить ссылку между
страницами для штатной интеграции не требуется.

Основа уже существует: `Core::apiHooks()` и `Api\HookStore` создают входы
`/api/hooks/<секрет>`, меняют настройки, включают и отключают, перевыпускают
секреты и удаляют записи. `Api\HookRegistry` проверяет принадлежность файлов
установленному модулю. Предлагается дополнить этот механизм модульным контекстом
владения и стабильным ключом входа, а не создавать второй реестр webhook.

Модуль описывает допустимые входы: ключ, название, обработчик, HTTP-методы,
способ проверки отправителя и необходимые параметры. При включении нужной
интеграции он просит менеджер создать или получить конкретный вход.
Описание возможности не означает, что все необязательные входы автоматически
открываются сразу после установки.

Условный пример будущего API, которого пока нет:

```php
$hook = $this->webhooks()->ensure('updates', [
    'handler' => 'hooks/updates.php',
    'methods' => ['POST'],
]);

$hook->enable();
$hook->disable();
$hook->rotateSecret();
$hook->delete();
```

Ключ уникален внутри модуля; при нескольких аккаунтах или подключениях
добавляется стабильный ключ экземпляра. Повторный `ensure()` и обновление
модуля не создают дубликат, не меняют секрет и не отменяют явно выбранное
отключение. Включение выполняется отдельной операцией настройки интеграции.

Контекст разрешает управлять только входами своего владельца. Текущий
`HookStore` работает с общими ID, поэтому ограничение владельца и атомарное
обеспечение уникальности ключа ещё нужно спроектировать. Простая передача ID
из формы без проверки владельца недостаточна. Управляющие действия модуля
доступны администратору с проверкой CSRF; входящий webhook не получает права
управления ни своими входами, ни админкой.

Публичный URL строится по настроенному внешнему адресу системы и префиксу
установки. Публичная точка входа использует существующую ветку `/api/hooks/`,
а не маршрут админки. Регистрация не создаёт домен, HTTPS или проброс порта:
доступность внешнего адреса — общесистемная настройка. Отдельный PHP-файл
в `public/` и отдельное правило nginx для каждого модуля не нужны.

В настройках модуля можно показать его входы, состояние, последнее обращение
и ошибку, дать управление включением и перевыпуском. Общий раздел API остаётся
местом общей диагностики и отображает те же записи с владельцем. Изменения,
сделанные там, отражаются в модуле; второго независимого состояния нет.

**Полную ссылку нельзя восстановить из хеша.** Сейчас `HookStore` хранит
SHA-256 и возвращает исходный секрет только при создании или перевыпуске.
Для повторного показа адреса и автоматической регистрации у внешнего сервиса
предлагается отдельное защищённое хранение исходящего секрета управляемого
входа: шифрование общим инструментом секретов, ключ вне БД, доступ только
разрешённой операции. Проверка входящего запроса по-прежнему использует хеш.
Это новое проектное решение, а не существующая возможность `HookStore`.
Оно требует отдельной реализации управления ключом; помещать полную ссылку
в обычные настройки, паспорт, общий JS-контекст или журналы не предлагается.
До такого решения повторное получение URL без перевыпуска обещать нельзя.

Публикация локального входа и регистрация адреса у внешнего сервиса — отдельные
шаги одной интеграции. Если сервис поддерживает управление через API, адаптер
модуля сам передаёт ему полученный URL и нужные параметры. Пользователь нажимает
«Подключить» в модуле. Если автоматической регистрации у сервиса нет, модуль
показывает адрес и необходимые действия именно в своих настройках.

Регистрация снаружи может завершиться ошибкой после создания местного входа.
Состояния различаются: вход подготовлен, ожидается регистрация, подключён,
ошибка регистрации. Повторная попытка использует тот же вход. Перевыпуск
секрета требует обновить адрес у внешнего сервиса; успех не показывается,
пока внешний шаг не выполнен. Формат подписи и особенности протокола остаются
в модуле, а общие проверки метода, размера запроса и частоты — в ядре.

При отключении модуля его входы перестают принимать запросы. При полном
удалении отзываются входы, удаляются их настройки, секреты и диагностические
данные. Если внешняя регистрация была выполнена модулем, он пытается снять её
до уничтожения необходимых учётных данных. Недоступность внешнего сервиса
не оставляет местный вход открытым; незавершённый внешний шаг отображается
явно. Поведение повторов и завершения такого удаления ещё требует решения.

## 9. Миграции модуля

Миграции принадлежат модулю и поставляются с его версией. Общий исполнитель
может переиспользовать подход миграций ядра, но не смешивать их идентификаторы.
Возможный ключ журнала: идентификатор модуля плюс версия миграции.

Обсуждаемые свойства:

- первая установка проходит всю цепочку, обновление — только недостающие шаги;
- применённый файл не переписывается и не переименовывается; исправление
  поставляется следующей миграцией, изменение контрольной суммы диагностируется;
- успешность фиксируется после выполнения шага, ошибка останавливает активацию;
- шаг можно безопасно продолжить или повторить после частичного сбоя;
- SQL используется для собственных данных, системные сущности меняются через
  штатные сервисы ядра с учётом владения;
- обновление данных не выдаётся за атомарное вместе с файловыми операциями:
  DDL MySQL может делать неявный commit;
- удаление модуля не означает выполнение всех миграций в обратном порядке.
  У него отдельный сценарий очистки по актуальному перечню ресурсов.

Откат кода после необратимой миграции может быть невозможен. Менеджеру нужен
честный статус ошибки и путь восстановления, а не обещание универсального
автоматического отката.

## 10. Учёт владения и готовые инструменты

Манифест описывает статические ресурсы, а общий реестр учитывает фактически
созданные, в том числе динамические. У записи есть владелец, тип, точный ключ,
политика удаления и при необходимости другие потребители.

| Инструмент для модуля | Что он помогает учитывать и очищать |
| --- | --- |
| Настройки по схеме | Значения, секреты и настройки по умолчанию |
| Работа с файлами | Собственные данные, кеш, временные и опубликованные файлы |
| Миграции | Версии схемы и собственные таблицы |
| Привязки свойств | Связи модуля с объектами через существующий API |
| События и обработчики | Подписки, принадлежащие модулю |
| Планировщик и очередь | Таймеры, задания, повторения и отложенная работа |
| Циклы | Запуск, остановка, состояние и диагностика |
| Объекты и классы | Происхождение сущностей и связи с другими потребителями |
| Меню, маршруты, UI | Регистрации, загрузка ассетов и общий Alpine |
| Webhook | Публикация своих входов, состояние, секреты и отзыв доступа |
| Ошибки и журнал | Контекст модуля без утечки секретов |

Это обёртки или расширения существующих сервисов `Core::*`, а не второй
планировщик, новая очередь или альтернативная система свойств.
Контекст владельца передаётся и фоновой работе. Создание ресурса и регистрация
владения согласуются транзакцией там, где возможно, либо восстанавливаемым шагом.

Удалять по похожему имени, префиксу таблицы или произвольному пути из архива
нельзя. Файловые операции ограничиваются разрешёнными каталогами; пути и ссылки
проверяются до копирования и удаления. Совместное использование отражается в
реестре: факт создания модулем ещё не разрешает сломать чужого потребителя.

### 10.1. Системные сущности и собственные записи модуля

Для классов, объектов, свойств и методов предлагаются готовые операции ядра:
найти, создать, изменить и удалить с предусмотренной системной очисткой.
Запись значения свойства использует существующий механизм свойств, включая
кеш, историю, аудит и доставку изменений. Модуль не обновляет `pvalues` напрямую.
Если нужной операции нет, она дополняет общий сервис и становится доступна
остальным модулям.

Для собственных данных достаточно небольшого инструмента запросов и CRUD:
выборка с фильтрами и пагинацией, поиск по ключу, вставка, изменение, удаление,
транзакции. Он работает с объявленными собственными таблицами, передаёт значения
параметрами и учитывает разрешённые поля. Валидация и авторизация действий
остаются необходимыми; проверка списка полей не заменяет их.

Например, Keenetic определяет данные роутеров и подключений, а Yandex Home —
собственные записи и настройки экспорта. Ядро обслуживает хранение, не придавая
этим записям общего системного типа «устройство». Специфические запросы могут
оставаться в слое данных модуля; большая универсальная ORM пока не требуется.

### 10.2. Привязка с собственным идентификатором

Ключ привязки обозначает конкретный источник внутри модуля, например
`connection:42:status`. Вместе с контекстом `keenetic` и целью `Router.internet`
этого достаточно для учёта связи без знания ядром смысла подключения.

Условный пример будущего API, которого пока нет:

```php
$this->bindings()->replace(
    "connection:{$connectionId}:status",
    $object,
    $property
);
```

Одна операция проверяет цель, заменяет старую связь и учитывает владельца.
Несколько источников одного модуля могут ссылаться на одно свойство: удаление
одного источника не снимает подписку, пока остаются другие. Менеджер может
получить все связи модуля и гарантированно снять их при полном удалении.
Работа со сменой привязки должна быть согласованной и восстанавливаемой.

Существующий API `addLinkedProperty()` / `removeLinkedProperty()` остаётся
основой совместимости. Новому слою нужен более точный учёт источников:
одного имени модуля в подписке для этой задачи недостаточно. Направление
передачи, преобразование значений и защита от обратной записи должны быть
описаны явно; протокольные преобразования остаются в модуле.

### 10.3. Задания как вызовы методов с данными

Предлагается давать разработчику постановку именованного задания с методом
и сериализуемыми аргументами. Собирание строки исполняемого PHP, подключение
класса модуля и создание экземпляра берет на себя штатный исполнитель.
Условный пример будущего API:

```php
$this->jobs()->later(
    "reboot:{$routerId}",
    'reboot',
    ['routerId' => $routerId],
    $seconds
);
```

Диспетчер проверяет разрешённый обработчик и состояние модуля, передаёт
аргументы по заранее определённому контракту; произвольный публичный метод
не становится автоматически доступной командой. Ключ задания получает область
имён владельца. Отмена, повторы и удаление всех заданий выполняются общим
планировщиком. Это дополнение существующей очереди, не параллельный исполнитель.

### 10.4. Установка обычного модуля без ручной уборки

Типовые подписки, настройки, расписания, меню и исходные классы со свойствами
можно описывать декларативно. Менеджер применяет описание и учитывает ресурсы;
особый код жизненного цикла нужен только для дополнительных действий.
Встреченная существующая сущность не объявляется автоматически собственностью
модуля. Повторная установка и обновление не должны затирать пользовательские
изменения методов без явной политики обновления.

После покрытия типовых ресурсов собственный `uninstall()` простого модуля
может вообще не понадобиться: менеджер снимает связи и очищает учтённые ресурсы.
Особое удаление не заменяет общий учёт владения и не должно его обходить.

### 10.5. Примеры, на которых обсуждался API

В соседних репозиториях `majordomo-*` точечно просмотрены существующие сценарии:

- Keenetic вручную меняет привязки и ставит таймеры со строками PHP;
  это пример для точного учёта связей и вызовов методов через планировщик.
- Tuya обслуживает несколько циклов и меняет схему в установке; это проверка
  достаточности общих средств для более сложного модуля.
- Telegram отдельно проверяет наличие столбцов и индексов; это пример для
  последовательных миграций модуля.
- Yandex Home уже имеет отдельный слой доступа к своим записям, но сохраняет
  ручные запросы и обслуживание привязок.
- В MQTT `dbInstall()` описывает `mqtt` и `mqtt_history`, а собственный
  `uninstall()` явно удаляет только `mqtt`. Это иллюстрация того, почему список
  созданных таблиц полезно получать из учёта ресурсов.

Keenetic подходит для обсуждения первого примера: собственные записи,
системный класс, свойства, события, связи и задания. Это предложение для
обсуждения, не поручение менять модуль.

## 11. Возможный ход установки и обновления

1. Получить конкретную версию пакета и проверить структуру и требования без
   исполнения его PHP-кода.
2. Получить общую блокировку изменения зависимостей и блокировку модуля,
   согласованную с системным деплоем; рассчитать изменения и зависимости.
3. В отдельной области подготовить код, PHP-пакеты и браузерную сборку.
   Ошибки сети и конфликт версий пока не затрагивают работающий модуль.
4. При обновлении закрыть приём новой работы модуля, остановить циклы и дождаться
   завершения либо управляемой отмены уже выполняемых заданий.
5. Применить миграции и дополнительные действия жизненного цикла. Записать
   ресурсы и выполненные шаги вне удаляемого каталога модуля.
6. Согласованно активировать код, зависимости, ассеты и регистрации, проверить
   готовность, затем разрешить приём работы и включить фоновые задачи.
7. Только после успеха зафиксировать установленную версию и отправить событие
   завершения. Удалить временные файлы подготовки.

Возможные состояния: подготовка, установка, активен, отключён, обновление,
удаление, ошибка. Конкретные имена пока не выбраны.
При ошибке остаётся достаточно служебного состояния для диагностики и
продолжения; незавершённая операция не помечается успешной.

Долгая операция не должна зависеть от открытого окна браузера или PHP-запроса
страницы. Отключение модуля сохраняет данные, но останавливает его работу.
Полное удаление — отдельное действие с другой семантикой.

## 12. Полное удаление — без оставленных данных модуля

Пожелание владельца: после успешного полного удаления ничего специально не
оставлять для будущей переустановки. Нет режима «модуль удалён, его таблицы и
секреты сохранены». Связанные объекты рассматриваются отдельно.

Возможный порядок:

1. Проверить зависимости других модулей и сущностей. Если есть потребители,
   показать их и не начинать частичное удаление без разрешения конфликта.
2. Показать связанные объекты и получить решение об их удалении или сохранении.
   Отмена диалога отменяет операцию до разрушительных шагов.
3. Запретить новую работу модуля, убрать внешние точки вызова, остановить циклы,
   завершить или отменить исполняемые задания. Сначала исключить повторное
   создание данных остановленным обработчиком.
4. **Всегда снять все привязки модуля**, независимо от решения по объектам.
   Удалить его подписки, таймеры, отложенные и повторные задания, собственные
   webhook-регистрации и другие точки повторного запуска.
5. Удалить собственные записи, таблицы, настройки, секреты, файлы данных,
   кеш, журналы модуля и состояние циклов. Очистку системных сущностей выполнять
   их штатными сервисами, а не произвольным SQL из деинсталлятора.
6. Обработать объекты по выбранному решению, проверить зависимости классов,
   свойств и методов. Сохранённые объекты не должны сохранять вызовы удалённого
   кода или зависеть от удалённого класса без явно согласованного преобразования.
7. Пересчитать пакетные зависимости, удалить только больше никому не нужные
   пакеты. Обновить согласованные lock-файлы и автозагрузку.
8. Удалить публикации ассетов, меню, маршруты, документацию модуля, исходный
   пакет, записи его миграций, маркеры и записи регистрации.
9. Проверить отсутствие принадлежащих ему ресурсов, удалить временные копии
   операции и её служебное состояние; только затем сообщить об успехе.

Исполнитель и описание очистки доступны до завершения операции, даже если
часть файлов уже убрана. При ошибке удаление можно продолжить; незавершённые
остатки видны как ошибка, а не скрываются сообщением «удалено».

Сохранение выбранных пользователем объектов — явное исключение из полной
очистки: они становятся независимыми от удалённого модуля. Чужие объекты,
общие таблицы и ресурсы других модулей не удаляются по совпадению имени.
В уже существующих сторонних резервных копиях менеджер не может автоматически
стереть прошлое; новые скрытые копии удалённого модуля он не оставляет.

## 13. Совместимость со старыми модулями

Новый формат можно распознавать по версии паспорта. При его отсутствии остаётся
текущий режим со старыми классами, URL, шаблонами и публичными функциями.
Не нужно переписывать все модули одновременно.

Для перехода конкретного модуля нужен разовый шаг принятия известных ресурсов
под управление. Применять миграции чистой установки поверх существующей схемы
без проверки нельзя. Владение старой таблицей или объектом подтверждается
явно, а не угадывается по имени.

Обещание удаления без остатков применимо к ресурсам, учтённым новым механизмом.
Для произвольного legacy-кода необходима отдельная инвентаризация; один новый
менеджер не узнает автоматически, что старый установщик когда-то записал.

## 14. Что ещё предстоит обсудить

- Где хранится служебный Composer-проект установки, как он включает пути
  автозагрузки ядра и локальные пакеты и согласуется с системным обновлением.
- Как выполняется переключение кода и автозагрузки на Linux и Windows и как
  при этом координируются PHP-процессы, циклы и системный деплой.
- Какой минимальный формат паспорта достаточен первому модулю, без лишних слоёв.
- Что означают «сохранить объект» и «удалить объект», когда его класс или методы
  принадлежат модулю, а объект используют пользовательские сценарии.
- Нужна ли поставка готовых проверенных ассетов для установок без Node.js.
- Как задаётся доверие к источникам пакетов и разрешённым шагам их сборки.
- Как хранится исходный секрет управляемого webhook для повторного получения
  URL и регистрации снаружи, где находится ключ шифрования и как он восстанавливается.
- Как завершается удаление при недоступности внешнего сервиса, в котором
  модуль ранее зарегистрировал свой webhook.

Будущая проверка идеи могла бы включать установку с нуля, обновление через
несколько версий, конфликт общей библиотеки, сбой миграции, прерванную операцию,
повторное удаление и оба решения по объектам. Отдельно — `partLoad`, один
экземпляр Alpine и отсутствие фоновой работы после удаления. Это идеи для
будущих проверок, а не поручение агентам создавать или запускать их сейчас.

> Ничего из него не внедрять и не использовать как ориентир без отдельного
> прямого поручения владельца.**
