# Маршрутизация модулей в стиле Laravel

Дата обсуждения: 2026-10-26. Статус: **Запланировано**.

## Цель

Получить в ядре один HTTP-роутер с привычным для Laravel API, чтобы модуль
объявлял свои страницы и обработчики в собственном пространстве путей. Новый
маршрут не требует правки `lib/admin_router.php` или отдельного файла в
`public/`; маршрут сам объявляет HTTP-методы, обработчик, имя и политику
доступа, а ядро обеспечивает 404/405, проверку входа и CSRF, кэш и запрет
выхода за префикс модуля.

Речь именно об HTTP-маршрутах. Методы объектов MajorDoMo (`Class.method`)
этим механизмом не управляются. Установка Laravel целиком, Blade, контейнер
зависимостей и произвольные маршруты из админки в задачу не входят.

## Что уже есть

- `public/nf.php` и `lib/admin_router.php` — таблица «regex → legacy query».
  Маршруты всех модулей лежат в одном файле ядра и добавляются правкой ядра.
- Общие правила `/panel/<module>.html` и `/panel/<module>/<id>.html` уже
  существуют, но дальше модуль сам разбирает `view_mode`, `id` и `tab`.
- Старые входы `?action=...&ajax=1` и `/modules/<module>/*.php` остаются
  рабочими; во втором случае URL напрямую соответствует PHP-файлу.
- API v1 строится из каталога `Contract::operations()` и `Dispatcher`.
  Общий маршрут `/api/v1/module/{module}` передаёт хвост пути в
  `module::api($params)`; своих маршрутов, имён и ограничений методов у
  модуля нет.
- `HookRegistry` уже умеет безопасно находить PHP-обработчик внутри
  установленного модуля и не выпускать путь за его каталог. Это можно
  переиспользовать для проверки границ, но это не роутер.
- `AuthGate` проверяет вход администратора, `AccessPolicy` — доступ к API.
  `RequestGuard` проверяет same-origin и CSRF, но ради старых модулей
  допускает изменения через GET. Новым маршрутам нужны более строгие правила.

## Предлагаемое решение

### 1. Роутер ядра

Добавить `MajorDoMo\Core\Routing\Router` с небольшим API в стиле Laravel:

- `get()`, `post()`, `put()`, `patch()`, `delete()`, `match()`;
- параметры пути `{id}` и необязательные `{id?}`, ограничения через
  `where()` / `whereNumber()`, но без пользовательских regex из запроса;
- группы с `prefix()`, `name()`, `middleware()`, `withoutMiddleware()`;
- именованные маршруты и генерация URL с учётом `ROOTHTML`;
- автоматический `HEAD` для `GET`, автоматический `OPTIONS` с `Allow`;
- честные `404` для неизвестного пути и `405` с заголовком `Allow` для
  известного пути с неподдерживаемым методом;
- единый конвейер middleware: установка, обслуживание, вход, CSRF,
  активность модуля, ограничение частоты, проверка политики.

Роутер не должен быть вторым HTTP-парсером: объект запроса и формат ответа
переиспользуют существующие `Api\Request` / `Api\Response` либо выделяются
из них без изменения контрактов API v1.

### 2. Регистрация маршрутов модулем

Модуль может добавить необязательный файл `modules/<name>/routes.php`:

```php
<?php

use MajorDoMo\Core\Routing\ModuleRoutes;
use MajorDoMo\Core\Routing\Router;

return static function (ModuleRoutes $routes): void {
    // Верхняя граница для всего модуля: маршрут с другим HTTP-методом
    // не регистрируется и попадает в диагностику.
    $routes->allowMethods(['GET', 'POST']);

    $routes->admin(function (Router $router): void {
        $router->get('/', 'KeeneticPage@index')->name('index');

        $router->get('/routers/{id}', 'KeeneticPage@router')
            ->whereNumber('id')
            ->name('router');

        $router->post('/routers/{id}/reboot', 'KeeneticPage@reboot')
            ->whereNumber('id')
            ->name('reboot');
    });
};
```

Ядро само добавляет префикс и пространство имён:

- `admin` → `/panel/<name>/...`; имя `keenetic.index`;
- `api` → `/api/v1/module/<name>/...`; имя `keenetic.api.*` (следующий этап);
- `public` → `/module/<name>/...`; только после отдельного решения по
  безопасности и nginx (последний этап).

Примеры URL (способ вызова генератора ещё уточняется):

```php
\MajorDoMo\Core\Core::router()->url('keenetic.router', ['id' => 12]);
// /panel/keenetic/routers/12.html

\MajorDoMo\Core\Core::router()->url('keenetic.reboot', ['id' => 12]);
// /panel/keenetic/routers/12/reboot
```

Панельные GET-страницы генерируются с `.html`; для действий суффикс не
добавляется, но входящий `.html` может приниматься для совместимости. Точное
правило фиксирует роутер, а не каждый модуль.

Обработчик задаётся строкой `Class@method` или парой `[Class::class,
'method']`. Замыкания в объявлениях маршрутов модуля не используются: таблицу
нужно сериализовать в кэш. Регистрационный файл может использовать замыкания
для группировки, но не должен писать в БД, выводить текст или менять
глобальное состояние. Регистрация выполняется кодом установленного модуля
при сборке таблицы, а не через админку или запись в БД: произвольный маршрут
из браузера создать нельзя.

Классы модуля должны быть доступны автозагрузкой. Нужен единый способ:
например, `modules/<name>/src/` → `MajorDoMo\Modules\<Name>\` или явная
автозагрузка в `routes.php`. Прямое подключение файла по URL не допускается.

### 3. HTTP-методы

- Метод объявляется явно; маршрута «на все методы» в первой версии нет.
- `GET` обязан быть безопасным и не менять данные. Новые маршруты не
  наследуют legacy-привычку менять состояние через GET.
- `POST`, `PUT`, `PATCH`, `DELETE` по умолчанию требуют действующий
  CSRF-токен. Same-origin и локальная сеть сами по себе не являются
  разрешением.
- `HEAD` обслуживается `GET` без тела; `OPTIONS` возвращает `Allow`.
- `TRACE` и `CONNECT` запрещены всегда.
- Подмена метода через `_method` не поддерживается: это лишний обход
  проверки методов.
- Если модуль разрешил только `GET` и `POST`, попытка объявить `DELETE`
  должна приводить к ошибке регистрации, а не к «тихому» включению метода.
- При ошибке регистрации модуль не должен получать частично работающие
  маршруты: лучше закрыть все его маршруты и записать понятную диагностику,
  чем открыть лишний обработчик.

### 4. Доступ и ответы

Для панельных маршрутов действует существующий вход администратора.
Роутер дополнительно проверяет, что запрос пришёл в сеансе администратора,
и не полагается только на то, что `nf.php` уже вызвал `AuthGate`.

Для API-маршрутов действует существующая модель `AccessPolicy`: токен,
пользовательский токен или проверенный сеанс, если это явно разрешено.
Ответ — JSON в существующем конверте API.

Публичные маршруты в первом этапе не открываются. Позже для них нужен
явный признак `public`, ограничение частоты и один из вариантов:
подпись, токен, секрет webhook. Для внешних интеграций уже есть
`/api/hooks/<секрет>`; новый роутер не должен становиться способом обойти
его проверки.

Обработчик возвращает объект ответа (`Response::html()`, `Response::json()`,
`Response::redirect()`, `Response::noContent()`), а не печатает текст и не
вызывает `exit`. Для панельной страницы нужен отдельный вариант ответа,
который передаёт заголовок, содержимое и подключаемые ассеты оболочке
`panel`, а не собирает второй HTML-каркас.

### 5. Интеграция с ядром

1. `RouterApplication` забирает у процедурного `nf.php` разбор пути и
   сначала пробует новые маршруты модулей.
2. Если нового маршрута нет, используется прежняя таблица
   `mdj_admin_route_table()`; старые URL и `pd` продолжают работать.
3. Затем вызывается `AdminApplication` или `SiteApplication`, как сейчас.
4. Панельные маршруты модулей живут под `/panel/`, поэтому новые правила
   nginx не нужны. Для будущего `/module/` понадобится отдельная location,
   запрет прямого исполнения PHP и проверка статики.
5. API-маршруты модулей встраиваются перед общим
   `/api/v1/module/{module}`; если у модуля нет нового маршрута, остаётся
   прежний вызов `module::api($params)`.
6. `part_load` и `MDJAdminUI` должны либо поддерживаться новыми панельными
   маршрутами, либо явно не обещаться в первом этапе. Молчаливый переход на
   полную страницу вместо фрагмента недопустим.

Перевод всех старых правил из `lib/admin_router.php` в новый роутер — не
условие первого этапа. Таблица остаётся совместимым слоем, пока модули
переходят по одному; удалять её можно только после проверки всех старых
ссылок.

### 6. Кэш, CLI и диагностика

- Скомпилированная таблица хранится в `cms/` (например,
  `cms/cached/routes.php`), без замыканий и без секретов.
- Ключ кэша включает версию ядра и время изменения `routes.php`; если у
  пакета есть версия, учитывается и она. Запись атомарная: временный файл и
  переименование.
- Кэш пересобирается при установке, обновлении, отключении и удалении
  модуля. Отдельная команда очистки нужна для диагностики.
- CLI в общем стиле проекта: `routes:list`, `routes:check`, `routes:clear`.
  `routes:list` показывает модуль, метод, путь, имя и область; `--json`
  нужен для тестов. `routes:check` проверяет конфликты, границы префикса и
  существование обработчиков.
- Ошибка регистрации попадает в «Ошибки системы» с модулем и маршрутом, но
  без файловых путей и секретов в ответе пользователю.
- Кэш не является проверкой доступа: сессия, CSRF и политика проверяются
  при каждом запросе.

### 7. Безопасность и границы

- Маршрут модуля не может выйти за `/panel/<name>/`, `/api/v1/module/<name>/`
  или `/module/<name>/`.
- Зарезервированные пути ядра (`/panel/`, `/api/v1/`, `/install`, `/ws`,
  `/assets`, `/cms`, `/docs`) нельзя перекрыть маршрутом модуля.
- URL не превращается в путь к файлу: только объявленный обработчик.
- Класс и метод обработчика проверяются на существование и допустимость;
  файл обработчика остаётся внутри каталога установленного модуля.
- Кодированные слэши, `..`, нулевые байты и обратные слэши отклоняются.
- Длина пути, число параметров и сложность шаблона ограничены; regex задаёт
  автор модуля, но не пользователь запроса.
- Тело запроса и JSON ограничиваются теми же лимитами, что API и nginx.
- Для дорогих и публичных действий нужен ограничитель частоты; значения по
  умолчанию должны быть консервативными.
- Ошибки не раскрывают физические пути, SQL и содержимое `.env`.
- Кэш маршрутов недоступен по HTTP и не должен быть записываемым для
  веб-пользователя сверх необходимого.

### 8. Совместимость

- Старые `/panel/<module>.html`, `/panel/<module>/<id>.html`,
  `?action=...`, `?md=...`, `pd`, `part_load` и `$action` продолжают
  работать без изменений.
- Общие правила `/panel/<module>.html` остаются запасным вариантом для
  модулей без `routes.php`.
- Старый `/panel/<name>.html` остаётся прежним входом; новый индекс —
  `/panel/<name>/`. Перекрытие существующего generic URL модуля допускается
  только явным алиасом или редиректом, а не побочным эффектом регистрации.
- `parseLinks()` и `module::redirect()` не меняют поведение; новый
  генератор URL используется только в новом коде.
- API v1 сохраняет существующие маршруты, формат ошибок и вызов
  `module::api($params)`.
- Новых Composer-зависимостей в первом этапе нет; проект остаётся на PHP 8.1.
- Код роутера — универсальная операция в `lib/core/`, а не перенос логики
  конкретного модуля в ядро.
- Старые `/modules/<module>/*.php` пока не удаляются. Новые маршруты не
  должны добавлять новые точки входа такого вида.
- Удаление или отключение модуля немедленно убирает его маршруты и
  инвалидирует кэш; старые ссылки получают 404, а не обработчик удалённого
  модуля.

### 9. Этапы

1. **Роутер и тесты.** `Router`, `Route`, `Response`, компиляция шаблонов,
   404/405, middleware, кэш, CLI. Без подключения к HTTP-входу.
2. **Панельные маршруты модулей.** `RouterApplication`, `routes.php`,
   `ModuleRoutes::admin()`, проверка входа и CSRF, ответ для оболочки
   `panel`, совместимый fallback на старую таблицу.
3. **API-маршруты модулей.** `ModuleRoutes::api()`, встраивание перед общим
   `/api/v1/module/{module}`, при необходимости — метаданные для OpenAPI.
4. **Публичные маршруты.** `/module/<name>/`, nginx, ограничение частоты,
   подпись или токен, отдельный разбор рисков. Только после этапов 1–3.
5. **Постепенный перевод ядра.** Сначала новые модули, затем основные
   правила админки; удаление старой таблицы — отдельное решение.

Первый этап можно сделать без изменения пользовательских URL. Это снижает
риск: сначала появляется механизм и тесты, потом — реальные маршруты.

## Открытые вопросы

1. Свой роутер или `illuminate/routing`? Пакет даёт готовую семантику, но
   тянет контейнер, Symfony HTTP и версионные ограничения: ветка 10.x
   совместима с PHP 8.1, ветка 12.x требует 8.2+. Для PHP 8.1 и
   legacy-загрузчика предпочтителен свой небольшой слой; решение о пакете
   остаётся открытым.
2. Точные префиксы и области: `/panel/<name>/` сейчас, `/api/v1/module/<name>/`
   и `/module/<name>/` позже. Нужно решить, будет ли `.html` обязательным
   для панельных страниц и как он сочетается с действиями.
3. Как панельный маршрут возвращает содержимое: отдельный `PanelPage`
   с заголовком и ассетами или обычный HTML, который оболочка вставляет
   через `part_load`? От этого зависит поддержка `part_load`.
4. Как модуль объявляет автозагрузку своих классов: жёсткая схема
   `modules/<name>/src/` или `composer.json`/будущий манифест модуля.
   Нужно ли проверять обработчики при сборке кэша или только при вызове.
5. Публичные маршруты: какой способ аутентификации считать основным,
   нужны ли они вообще при наличии `/api/hooks/<секрет>` и как учитывать
   локальную сеть.
6. `route()` как глобальная функция или только
   `MajorDoMo\Core\Routing\route()` / `Core::router()->url()`? Глобальное
   имя может конфликтовать со старыми модулями.
7. Формат кэша и поведение при нескольких серверах: локальный кэш,
   общий Redis или пересборка при деплое. Что делать при повреждённом кэше.
8. Должны ли API-маршруты модулей попадать в общий OpenAPI и кто отвечает
   за схемы запроса и ответа.
9. Нужны ли `PUT`/`PATCH`/`DELETE` в первом этапе или достаточно `GET` и
   `POST`, как в большинстве текущих модулей.
10. Нужен ли стриминг и скачивание файлов через `Response`, или в первом
    этапе ограничиться HTML/JSON/redirect.
11. Что делать со старыми GET-действиями, которые меняют состояние:
    оставлять их на legacy-маршрутах до отдельной миграции или запрещать
    в новых `routes.php`.
12. Нужна ли политика на уровне объекта/свойства (`can`) уже сейчас или
    достаточно проверки администратора и модуля.

## Критерии готовности первого этапа

- [ ] Тестовый модуль-фикстура регистрирует `GET` и `POST` в своём префиксе;
  корректный запрос получает ожидаемый ответ.
- [ ] Неизвестный путь внутри префикса даёт 404, неверный метод — 405 с
  `Allow`; `HEAD` и `OPTIONS` ведут себя предсказуемо.
- [ ] Маршрут вне префикса, дубликат пути или имени и метод вне
  `allowMethods` не регистрируются; ошибка видна в диагностике.
- [ ] Без сеанса администратора панельный маршрут не выполняется; `POST`
  без CSRF получает 403; публичного обхода нет.
- [ ] Старые `/panel/...`, `?action=...` и `pd`-ссылки работают;
  `php tests/routing_smoke.php` проходит.
- [ ] Установка, обновление, отключение и удаление модуля пересобирают или
  очищают кэш; обработчик удалённого модуля недоступен.
- [ ] Кэш не содержит замыканий и секретов, переживает повторный запрос и
  не требует загрузки всех `routes.php` на каждом запросе.
- [ ] `routes:list`, `routes:check`, `routes:clear` работают, `--json`
  пригоден для тестов.
- [ ] Тесты изолированы от рабочей БД и Redis и используют модуль-фикстуру,
  а не реальный модуль проекта.
- [ ] Для авторов модулей добавлена инструкция с примерами; после
  реализации обновлены `admin-routing.md` и `entrypoints.md`.
