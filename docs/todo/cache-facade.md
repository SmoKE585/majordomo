# Фасад Cache с TTL и сохранением типов

Дата обсуждения: 2026-10-25. Статус: **Запланировано**.

## Цель и требования

- [ ] Добавить API в стиле Laravel: `Cache::get()`, `put()`, `remember()`,
  `forget()`, `has()`. `remember` возвращает сохранённое значение либо
  вычисляет и кэширует результат callback.
- [ ] Поддержать TTL, массивы и сохранение типов, включая различие
  отсутствующего ключа, `false`, `0` и пустой строки.
- [ ] Использовать собственный namespace, предварительно
  `MajorDoMo\Core\Facades\Cache`, поверх общего сервиса ядра.
- [ ] Переиспользовать Redis и `Config`. Доработать `Core::cache()` либо
  выделить прикладной сервис: сейчас кэш отвергает массивы, объекты и `false`,
  хранит скаляры строками и не имеет TTL.
- [ ] Сохранить `checkFromCache`, `saveToCache`, `clearCacheData` и остальные
  старые функции с прежними контрактами и форматами хранения.
- [ ] Выделить отдельный префикс прикладного кэша. Его очистка не затрагивает
  свойства, метаданные, очереди, блокировки и состояние циклов.
  Не использовать `FLUSHDB`/`FLUSHALL` для прикладной очистки.
- [ ] Не публиковать незавершённые изменения БД в общий кэш; сохранить
  корректное чтение внутри транзакций.
- [ ] Добавить примеры и инструкции агентам. Массовую замену служебного кэша
  не включать автоматически в первый этап.

## Открытые вопросы

Определить единицы и границы TTL, трактовку `null`, формат сериализации
и поведение при отключении или отказе Redis. Хранилище без Redis должно
поддерживать обещанные TTL и типы; поведение legacy не менять незаметно.

Установка `illuminate/cache` и новые зависимости не утверждены: оценить,
нужен ли пакет или достаточно расширения существующего слоя. Гарантии
`remember` при одновременных запросах определить отдельно.

## Критерии готовности

- [ ] Проверены чтение, запись, истечение TTL, удаление, типы значений
  и `remember` при попадании, промахе и ошибке callback.
- [ ] Прикладной кэш и служебные ключи не влияют друг на друга.
- [ ] Старые функции сохраняют результаты и формат хранения.
- [ ] Проверки изолированы от рабочей БД и Redis; проверено поведение без Redis.
