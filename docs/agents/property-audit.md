# Журнал изменений свойств

## Коротко

Устройство всегда включённого журнала изменений свойств: какие таблицы он
пишет, как передаётся trace id и как открыть цепочку в админке. Читайте, когда
разбираете цепочку автоматизации или добавляете шаг в журнал.

Журнал включён всегда: отдельного `ENABLED`-флага нет. Отключать его нельзя,
потому что он является частью диагностики цепочек автоматизации. Настраивается
только срок хранения.

## 1. Зачем

Журнал отвечает на вопросы:

- кто/что изменил свойство;
- когда и в рамках какого запуска;
- какое значение было и какое стало;
- какой метод, сценарий или модуль выполнился до этого;
- какие параметры пришли в метод/сценарий и что вернулось;
- куда можно перейти, чтобы открыть метод, свойство, сценарий или модуль.

`phistory` остаётся историей значений для графиков и включается через
`KEEP_HISTORY`. Новый журнал — отдельный, всегда включённый поток фактов; он не
заменяет `phistory` и не требует `KEEP_HISTORY`.

## 2. Таблицы

Схема создаётся миграцией `20261023_property_audit_v1` в
`Migrations::ensurePropertyAuditSchema()` и присутствует в
`lib/core/Install/schema.sql`.

### `property_audit_runs`

Заголовок одного запуска:

- `ID`, `TRACE_ID` (32 hex);
- `STARTED`, `LAST_SEEN`, `FINISHED`, `STATUS`;
- `TRIGGER_TYPE` — `property`, `method`, `script`, `job`, `timer`, `module`,
  `event`; `resume` — продолжение запуска в `core_worker`;
- `TRIGGER_TITLE`, `SOURCE`, `ACTOR`, `IP`, `REQUEST_URI`;
- `PARAMS` — входные параметры запуска;
- `RESULT`, `ERROR`, `CHAIN`, `EVENTS_COUNT`.

Колонки `CHAIN` и `EVENTS_COUNT` есть в схеме, но текущая реализация их не
заполняет: цепочка хранится в каждом событии, а число событий считается
запросом при чтении.

### `property_audit_events`

Шаги запуска:

- `RUN_ID`, `TRACE_ID`, `ADDED`, `FINISHED`, `DURATION_MS`, `TYPE`, `STATUS`;
- `TITLE`, `SUBTITLE`;
- `OBJECT_ID`, `PROPERTY_ID`, `PROPERTY_NAME`;
- `METHOD_ID`, `CLASS_ID`, `SCRIPT_ID`, `MODULE`;
- `OLD_VALUE`, `NEW_VALUE`;
- `SOURCE`;
- `PARAMS` (вход), `OUT_PARAMS` (состояние после выполнения), `RESULT`;
- `ERROR`, `CHAIN`.

Типы событий: `trigger`, `job`, `method`, `script`, `module`, `property`,
`error`, `warning`, `chain`.

Свойство считается изменённым только при фактическом изменении значения.
Повторная запись того же значения по-прежнему доставляет `ONCHANGE` и
подписчикам, но новую строку «изменения» не создаёт.

## 3. Trace id и очередь

Запуск начинается в одном из мест:

- `Scheduler::execute()` — задача планировщика;
- `Methods::call()` / `Methods::callSafe()` — прямой или фоновый вызов метода;
- `runScript()` / `runScriptSafe()` — сценарий;
- `OperationWorker::execute()` — очередь `core_runtime`;
- `EventBus::drain()` — доставка системного события модульным подписчикам;
- `Properties::set()` — прямое изменение свойства без метода (ручное или API);
- `ApiClient` — синхронный внутренний API (`/api/method/*`,
  `/api/modulePropertySet/*`), если в параметрах есть `_trace`.

Внешний HTTP API (`public/api.php`) `_trace` не принимает: `ApiApplication`
вырезает его из query/body пользовательских запросов.

Дальше `_trace` передаётся через:

- `OperationsQueue` (payload `method` / `modulepropertyset` / `moduleevent`);
- `raiseEvent()` и `ONCHANGE`-параметры;
- `callMethodSafe()` и `runScriptSafe()`;
- `ApiClient` в `/api/method/*` и `/api/modulePropertySet/*`.

`PropertyChain` продолжает отвечать только за защиту от циклов свойств. Trace id
и цепочка шагов — отдельная ответственность `PropertyAudit`. Вместе с `_chain`
идёт служебная точка доставки `_delivery` (`module` + `point`): она говорит,
какому модулю и по какому свойству принадлежит текущий шаг, чтобы его эхо
гасилось только на этом свойстве.

С 25.10.2026 `_delivery` также может содержать `exclusions` — соответствие
«модуль → свойство» для переданного `NO_LINKED`. Оно сохраняется даже без
модуля-источника (например, при прямой входящей записи MQTT). Входящее событие
модуля с пустой `point` не подавляет уведомления этому модулю: метод или
сценарий может отправить команду другому его устройству. Защита от повторного
свойства в `_chain` при этом остаётся включённой.

В `NO_LINKED` может присутствовать служебная метка `@mdj:scope`: она отличает
унаследованные исключения от нового явного запрета текущей записи. В аудите
она остаётся видимой, чтобы объяснить снятие исключения на другом свойстве.

`OperationWorker` вызывает `PropertyAudit::enter($traceId)` для продолжения
родительского запуска и `PropertyAudit::begin()` только если trace отсутствует
(старые записи в очереди, внешние вызовы).

## 4. Что попадает в параметры

- Метод: `$params` до выполнения (без `m_c_s`, `r_s_m`, `r_s_s`, `raiseEvent`,
  `_trace`, `_chain`, `_delivery`), `OUT_PARAMS` после выполнения и возвращённый результат.
- Сценарий: входные `$params` и `OUT_PARAMS`.
- Задача: `COMMANDS` и результат `eval`.
- Модуль: `object/property/value` или `event/details`.
- Свойство: `OLD_VALUE`, `NEW_VALUE`, `SOURCE`, `CHAIN`.

С 23.10.2026 новые шаги методов и сценариев сохраняют `execution`: снимок кода,
SHA-256 полного кода, признак обрезки, а для методов — владельца и порядок вызова
родителя. Это код на момент входа в шаг; прежние записи снимка не имеют.
Код ограничен 24 КиБ. Вложенные шаги и записи свойств получают `parent_event_id`
для перехода к вызывающему шагу внутри текущего процесса. После очереди trace id
сохраняется, но локальный стек шагов начинается заново.

Служебные данные упакованы в версионированную оболочку `__mdj_audit_step_v1`
в существующей колонке `PARAMS`; при чтении она распаковывается, поэтому поле
`params` в API по-прежнему содержит только пользовательские параметры.
Новые колонки и миграции не нужны. Слишком большой JSON сохраняется валидным
превью с `_truncated: true`, а не оборванной строкой.

Явный результат `false` отмечает шаг ошибкой. Успешное завершение внешней обёртки
не снимает ошибку вложенного шага. Воркер также не подтверждает отказ метода
или сценария как успешное выполнение: операция проходит штатные повторы очереди.

Значения обрезаются до 64 КБ; для обычных домашних значений это полный объём.
Журнал не пытается редактировать секреты: не пишите пароли в свойства и
`$params`, если не хотите видеть их в диагностике.

## 5. API и UI

Endpoint находится в модуле «Объекты»:

```
GET /admin.php?action=objects&md=objects&view_mode=edit_objects&id=<object>&tab=properties
    &ajax=1&op=property_trace&property_id=<property>
    &trace_range=24h&trace_page=1
```

Ответ:

```json
{
  "status": "ok",
  "meta": {"object_id": 7, "property_id": 17, "property_name": "Lamp.status"},
  "range": {"key": "24h", "label": "24 часа"},
  "runs": [
    {
      "id": 12,
      "trace_id": "…",
      "trigger_type": "method",
      "trigger_title": "Lamp.onTimer",
      "started_label": "22.10.2026 16:13:00",
      "status": "done",
      "events": [
        {"type": "method", "method_id": 7, "params": {}, "result": true},
        {"type": "property", "old_value": "0", "new_value": "1"}
      ]
    }
  ],
  "pagination": {"page": 1, "total": 1}
}
```

Сервер сам добавляет к событиям `links` — готовые URL на метод, свойство,
сценарий или модуль. UI не строит маршруты повторно.

В карточке свойства кнопка **«Цепочка»** открывает `MDJUI::traceDrawer()`.
Компонент монтируется в общий drawer host (`20_drawer.js`), данные грузит
`resources/js/modules/admin_panel/41_trace.js`. Периоды: 3 ч, 12 ч, 24 ч, 7 дн.,
30 дн. По умолчанию открыт последний запуск; остальные — сворачиваемые
`<details>`, чтобы длинная история не занимала весь экран.

«Копировать запуск с кодом», «Копировать шаг» и «Копировать страницу» копируют
JSON загруженных данных с параметрами, результатами, ссылками и сохранённым кодом.
Страница — только текущая страница пагинации. Каждый блок параметров и кода
также имеет отдельное копирование. Изменения параметров показаны отдельно;
«К вызывающему шагу» переводит фокус на родительский шаг.

## 6. Retention

`PROPERTY_AUDIT_RETENTION_DAYS` в `.env` (по умолчанию `7`):

- `7` — хранить неделю: журнал растёт на каждое изменение свойства, и
  неограниченная таблица делает дорогим любой запрос, включая случайный скан;
- `0` — хранить бессрочно; это осознанный выбор, а не значение по умолчанию;
- другое положительное число — свой срок.

`startup_maintenance.php` удаляет старые события и заголовки запусков пачками
(по 5000 строк) и не трогает записи новее срока. Число пачек ограничено не
счётчиком, а бюджетом времени `prune(..., $seconds = 30)`: после снижения срока
на большой таблице журнал сокращается за считанные запуски `cycle_main`, а не за
десяток. Перед включением retention сделайте резервную копию БД, если журнал
нужен для разбора инцидента.

## 7. Гарантии и отказы

- Запись свойства не падает из-за журнала: все ошибки аудита перехватываются.
- Ошибка журнала показывается через `ErrorReporter` (код `property_audit`) не
  чаще одного раза за окно.
- Если таблицы ещё нет, `ensureSchema()` создаст её при первой записи; штатная
  миграция делает это раньше.
- Запись аудита синхронная. При очень высокой частоте изменений (сотни в
  секунду) её стоит перевести на батч/очередь; сейчас это осознанный компромисс
  ради простоты и надёжности.
- Поиск ошибки запуска в `finishRun()` идёт по `TRACE_ID`, а не по `RUN_ID`:
  `TRACE_ID` уникален для запуска и покрыт `idx_property_audit_events_trace`,
  а у `RUN_ID` индекса нет — запрос по нему читал весь журнал. Не возвращайте
  фильтр по `RUN_ID` без индекса: на большом журнале это полный скан на каждый
  завершённый запуск.
- Запуск может остаться в статусе `running`, если процесс был убит до
  завершения. Это факт, а не потеря изменения: события уже записаны.

## 8. Проверка

### Активность на главной

С 24.10.2026 `PropertyAudit::activityByTenMinutes()` считает строки типов
`property`, `method`, `script` по индексу `(TYPE, ADDED)`. `trigger` отдельно
не считается. Повторные события учитываются; ошибочные и ещё выполняющиеся
методы и сценарии входят в число запусков. `pvalues.UPDATED` и `scripts.EXECUTED`
для графика больше не используются.

Окно — последние 24 часа, шаг — 10 минут, крайние интервалы частичные.
Подсказка содержит дату и границы интервала в часовом поясе системы.
Если таблица журнала ещё не создана, UI показывает недоступность данных.
Общий payload кэшируется на 20 секунд, поэтому отдельно повторно журнал
для каждого посетителя не читается. Чтение графика не создаёт схему и события.

Redis проверяет `Core::redis()->diagnostics()`: PING отдельно от INFO;
отказ прав INFO не выдаётся за недоступность сервиса. Память, соединения,
операции и вытеснения относятся ко всему серверу, число ключей — к выбранной БД,
а не к префиксу установки. `maxmemory=0` означает отсутствие лимита.
Предупреждения памяти: от 80%, опасное состояние — от 90%.
Проверка сервера использует штатное соединение и его таймаут; выключенный Redis
не опрашивается. Рабочие сервисы автоматическими тестами не затрагиваются.

Проверки: `php tests/dashboard_smoke.php` (SQLite в памяти, подменный Redis),
`node tests/dashboard_browser_smoke.mjs` (локальные фикстуры, ApexCharts,
светлая/тёмная темы, 1440/390/360 px, повторный partLoad).

```bash
php tests/property_audit_smoke.php
php tests/method_inheritance_smoke.php
php tests/operation_result_smoke.php
node tests/property_trace_ui_smoke.mjs
php tests/property_onchange_smoke.php
php tests/property_delivery_smoke.php
php tests/stale_module_bindings_smoke.php
```

Проверьте вручную: откройте свойство → «Цепочка» → последний запуск, затем
перейдите по ссылке на метод и обратно. Журнал доступен и для свойств без
`KEEP_HISTORY`.
