# API ядра

**Коротко:** HTTP-API v1 обслуживает `public/api.php` через `ApiApplication`, а маршруты, валидация, описания панели и OpenAPI строятся из одного каталога `lib/core/Api/Contract.php`. Локальная сеть может работать без токена, внешние запросы требуют `Authorization: Bearer` или `X-API-Key`. Старые URL `/api/*` сохранены как совместимый адаптер.

Для агента-клиента: [инструкция по использованию HTTP API](api-client.md).
Пример nginx — `docs/deploy/nginx.conf.sample`: выделенный FastCGI location
сохраняет исходный URI, передаёт Authorization/X-API-Key/X-Forwarded-For,
не перехватывает JSON-ошибки PHP и возвращает JSON при лимите тела nginx.

`public/api.php` — только адаптер к `ApiApplication`. Последовательность:
config → InstallState → AccessPolicy → Request/JSON → loader/settings →
Core::apiDispatcher → Response. Ошибки и завершение legacy-кода перехватываются
на HTTP-границе: HTML и отладочный вывод не попадают в JSON. Секреты и тела
запросов не пишутся в аварийный журнал: используйте request_id.

Сбой API журналируется: непойманная ошибка (ответ 500) и осознанный 5xx
(например, 503 «билет WebSocket не выдан») регистрируются `FailureLog` как
`api_exception` / `api_unavailable` — в «Ошибках системы» и `errors.log` с
маршрутом, request_id, классом исключения, сообщением, файлом и стеком.
4xx, режим обслуживания и незавершённая установка в журнал не попадают.

`lib/core/Api/Contract.php` — источник маршрутов v1, схем валидации, описаний
панели и OpenAPI. Новую операцию добавляйте в каталог и Dispatcher; не заводите
независимый роутер/статическую копию документации. Публичная спецификация —
`/api/v1/openapi.json`; в разделе API панели её можно скачать (доступ к панели
закрывает reverse proxy, встроенной авторизации в приложении нет).
Формат соответствует [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html).

`/objects/` удалён. Его чтение и запись свойств, методы и сценарии доступны
через существующие `/data`, `/method`, `/script` в API v1. Добавлены POST
`/say`, `/say/reply`, `/say/to` и `/subscriptions/{event}`. Эти маршруты
вызывают функции ядра; `/subscriptions` принимает `details` и необязательный
`return_output` (boolean), возвращая результат обработчиков. Задания планировщика
исполняет только CLI-worker с токеном захвата, публичного HTTP-запуска задания нет.

Внутренние фоновые методы, сценарии, сообщения, подписки и уведомления модулей
не вызывают HTTP или API: `OperationsQueue::enqueueRuntime()` сохраняет параметры
и trace/chain, `OperationWorker` вызывает функции и сервисы напрямую.
`callAPI()` оставлен как публичная функция для явно запрошенных API-вызовов
и совместимости с дополнениями; существующие элементы очереди `api` поддерживаются.

`Dispatcher` не знает об HTTP-авторизации. В него можно войти только из уже
проверенного HTTP-входа или из доверенного PHP-кода. Флаг `internal`, заголовок,
имя хоста или query-параметр не дают привилегий. `ApiClient` относительные пути
обрабатывает локально, асинхронные операции кладёт в существующий core_runtime.
Новый тип задания `api` обрабатывает тот же OperationWorker. Исходные типы
`method` и `modulepropertyset` сохранены вместе с trace/chain.
Сегменты пути собирайте через `rawurlencode()`: `Api\Request` разбирает их через
`rawurldecode()`, а `urlencode()` кодирует пробел как `+` — путь не совпадёт с
названием сценария или метода.

Исключение по обработке: `/auth/login|me|logout` объявлены в том же Contract,
но исполняются `ApiApplication` → `UserAuthentication` до legacy loader.
Dispatcher отклоняет внутренний вызов auth-маршрута: идентичность и секреты
нельзя передать как параметры доверенного ApiClient. Пользовательский токен
`mdmu_` проверяется через `UserTokenStore`; actor `user_token` не даёт доступа
к panel-маршрутам. Механизм, сроки и безопасный профиль с объектом/классом —
[authentication.md](authentication.md), примеры клиента — [API](../user/api.md#вход-пользователя).

CORS для v1 проверяет `BrowserAccess` по BASE_URL и локальному Public Suffix
List: домен владельца и поддомены, тот же протокол, без cookie credentials.
С другого origin всегда нужен явный токен, даже из HOME_NETWORK. Login
публичен; OPTIONS не требует токена, но проверяет метод/путь через Contract и
разрешает только Authorization, X-API-Key, Content-Type. JSON-ошибки для
разрешённого origin также имеют CORS-заголовки. Legacy междоменно закрыт.

`AccessPolicy` использует `NetworkAccess`, HOME_NETWORK, TRUSTED_PROXIES.
Loopback (`127.0.0.1`, `::1`) всегда считается доверенным прокси, поэтому
схема «nginx → 127.0.0.1:80» работает без записи в `.env`; `TRUSTED_PROXIES`
добавляет только внешние прокси. Если HOME_NETWORK пуст, допускаются частные
сети IPv4/IPv6 и loopback. Если задан — только перечисленные сети плюс loopback.
XFF от недоверенного соединения не доказывает локальность; доверенный прокси без
достоверного оригинального адреса тоже требует токен. Применяется и к legacy URL.

`TokenStore` работает через prepared mysqli/PDO-запросы: веб использует
соединение ядра, CLI — ленивое отдельное подключение без legacy loader,
тесты — SQLite. Список не читает TOKEN_HASH, секрет возвращается только при
issue/rotate. Ротация использует compare-and-swap по старому хешу, отзыв
не восстанавливает токен. Админские действия — POST + отдельный session CSRF.
Полный секрет приходит только AJAX-ответом, не сохраняется в session/URL.

Таблица api_tokens создаётся при установке раздела и основной миграцией
20261024_core_api_v1. Та же миграция переводит locations в InnoDB, чтобы
перестановка и удаление с обновлением привязок были транзакционными. В новом
install/schema.sql обе схемы присутствуют. Не запускайте миграции на рабочей
БД для проверки: тесты используют SQLite/фикстуры.

`api_user_sessions` создаётся миграцией `20261026_api_user_sessions`, новой
установкой и `Schema::install()`. Хранятся только хеш токена и отпечаток
учётной записи. Истёкшие записи старше суток после EXPIRES_AT удаляются при
новом входе; EXPIRES_AT индексирован. Постоянные ключи не затрагиваются.

Совместимость legacy: /room и /rooms, setOrder, query/form, apiHandleResult,
setHandleResult, data/result, passed/timestamp. Внешние вызовы требуют токен.
В v1 изменение состояния не происходит через GET, исключение — произвольный
legacy API модуля, поведение которого определяет дополнение. Legacy выдаёт 400
для прежних ошибок поиска/валидации; v1 различает 404/405/422. Исправлены периоды
month/year (30 и 365 дней, без лишнего множителя 7).

## Служебный API панели

`/api/v1/panel/*` — внутренние операции админки: дашборд, поиск, консоль
X-Ray, уведомления, билет WebSocket и данные X-Ray. Маршруты объявлены в
`Contract::panelOperations()` и **не попадают** в OpenAPI и раздел API панели.
`Dispatcher` пускает сюда только `actor === 'session'`: API-токен и правило
локальной сети доступа не дают. Запись требует `X-CSRF-Token`, который
добавляет общий `fetch`-обёртчик `resources/js/modules/admin_panel/05_auth.js`.

Клиент — `resources/js/modules/admin_panel/07_api.js` (`window.MDJAdminApi`):
`dashboard()`, `updates()`, `search()`, `console()`, `dismissModuleNotifications()`,
`propertyHistory()`, `propertyTrace()`, `xray.content()`, `xray.service()`,
`xray.command()`, `xray.cycleLog()`, `xray.clearLogs()`, `xray.database()`,
`xray.stopTimer()` и другие методы. История и цепочка свойства объекта
(`/panel/objects/{object}/properties/{property}/history|trace`) делегируют
готовым сборщикам модуля «Объекты», поэтому формат ответа не меняется.
Старые `admin.php?ajax_panel=1&op=...`, `admin.php?action=xray...&ajax=1`,
`ajax/xray.html?action=service` и `ajax/saverestore.html?op=check_updates`
сохранены как тонкие адаптеры над `lib/core/Api/Panel.php`, `PanelSearch.php` и
`PanelConsole.php`; их логика больше не дублируется. X-Ray отдаёт данные теми же методами `admin()` и
`service_control()`, переключаясь в режим возврата массива.

## Входящие webhook

Вкладка «Входящие webhook» в разделе API (`/panel/api.html?tab=hooks`) создаёт
публичные входы вида `/api/hooks/<секрет>`. После секрета можно передать хвост
пути — `/api/hooks/<секрет>/v1.0/user/devices`: он становится `PATH_INFO`
обработчика, а `REQUEST_URI` — относительным (`/v1.0/user/devices`). Это
позволяет подключить Yandex Smart Home к тому же публичному входу, не поднимая
отдельный `server :7443`. Секрет — 64 hex-символа (`random_bytes(32)`, 256 бит).
В `api_hooks` хранится только SHA-256-хеш; полная ссылка и необязательный секрет
заголовка возвращаются один раз при создании или перевыпуске. Список показывает
только название, модуль/файл, методы и диагностику: время последнего обращения,
HTTP-статус и метод. Тела, заголовки, IP и полные URL не сохраняются.

Тип назначения хранится в `api_hooks.HANDLER_TYPE`: `module` (по умолчанию для
старых строк), `script` или `code`. Для module запись создаётся только для
**установленного** модуля (`cms/modules_installed/<name>.installed`)
и существующего `.php`-файла внутри `modules/<name>/`. Абсолютные пути, `..`,
stream wrappers и symlink за пределы каталога модуля отклоняются; проверка
повторяется при каждом вызове, а не только при сохранении.

Для script хранится SCRIPT_ID существующей записи `scripts`; вызов делегируется
штатному `runScript($id, $params)`, без копирования кода и без очереди. Наличие
сценария проверяется при сохранении и вызове. Для code хранится CODE, до 65535
байт PHP без тегов; `token_get_all(..., TOKEN_PARSE)` проверяет синтаксис без
исполнения при сохранении. Код исполняет `Core::code()` после штатного boot.
Неактивные поля назначения очищаются при смене типа; секрет ссылки не меняется.
`HookStore::all()` не выбирает CODE. POST админки `operation=hook_details`
проверяет CSRF и возвращает `editable()` без хешей секретов для редактора.

Порядок обработки в `ApiApplication`: config → install gate → распознавание
`/api/hooks/<secret>` → поиск записи по хешу → метод/заголовок/размер/частота →
загрузка loader/settings → include файла, runScript или Core::code(). Ветка стоит **до**
`AccessPolicy`, JSON-парсера и общего API; API-токен, локальная сеть и cookie
администратора здесь не дают доступа. `HookContext` открывает `AuthGate` только
на время этого проверенного вызова; по query-параметру, заголовку или одному
совпадению URI обход невозможен. HEAD после проверки метода и дополнительного
заголовка завершается 200 без загрузки runtime и вызова обработчика.

Обработчик получает исходные `REQUEST_METHOD`, `$_GET`, `$_POST`, `$_FILES`,
`php://input` и заголовки. Без хвоста пути `REQUEST_URI` очищается от секрета
(`[redacted]`); с хвостом он равен `PATH_INFO` (например, `/v1.0/...`) и секрета
не содержит. Для module `SCRIPT_FILENAME`/`SCRIPT_NAME` указывают на файл модуля, рабочий
каталог — корень проекта (как у публичных входов). Ответ не оборачивается в JSON
API: сохраняются HTTP-статус, `Content-Type` и заголовки, а `exit`/`die`
завершает запрос с уже сформированным телом. Ошибки границы webhook возвращаются
обычным JSON-конвертом и не раскрывают пути и SQL.

Для script/code возвращённый массив сериализуется как JSON без API-обёртки;
непустой echo приоритетнее return и отдаётся как HTML. null без вывода даёт
пустой ответ, другой тип return — 500 `invalid_webhook_result`. Статус и
дополнительные заголовки сохраняются, Content-Type определяется по результату.
Тела 204/304 подавляются. Проверка и исполнение не создают HTTP-сессию админа.
`$params` содержит только webhook_id, method, path; запрос читается через
суперглобалы/php://input, без копирования секретов в аудит сценария.
Для обработчиков script/code проверенный HookContext позволяет пробросить Exception до
API-границы; модульные webhook и другие запуски сохраняют прежний registerError. Иначе ошибка
сценария превратилась бы в пустой HTTP 200.

Публичный запрос не выбирает назначение: тип, сценарий и код задаёт только
администратор. Файловый обработчик должен быть штатным файлом установленного
модуля; код, рассчитанный на точный
`REQUEST_URI` без хвоста или на каталог модуля как cwd, может потребовать
адаптации. `PATH_INFO` после секрета поддерживается. Сессия администратора не
создаётся и `$session` автоматически не заполняется: обработчику, которому нужна
сессия, придётся открыть её самому. Приложение не проксирует HTTP, не принимает
URL назначения и не подменяет подтверждённый контекст безопасности данными
запроса.

Лимиты: разрешённые методы `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` (по
умолчанию POST), тело до 1 МиБ (как у nginx) и 120 обращений в минуту на вход
(файл `var/security/api-hooks.json`). `HEAD` — проверка доступности: после
проверки секрета ссылки и дополнительного заголовка граница отвечает 200 без
тела и без запуска обработчика; так платформа Яндекс периодически проверяет
Endpoint URL. Отключение, удаление и перевыпуск действуют сразу: запись читается
из БД на каждом вызове, кэша разрешений нет. Дополнительный секрет проверяется
в настраиваемом заголовке, например `X-Telegram-Bot-Api-Secret-Token`; значение
сравнивается по хешу.

NGINX: отдельное правило для каждого webhook не нужно, используется существующий
`location ~ ^/api(?:\.php)?(?:/|$)`. `client_max_body_size 1m` уже ограничивает
тело. Отдельный `server` для Yandex Smart Home больше не нужен: его URL —
`https://<host>/api/hooks/<секрет>`, а хвост `/v1.0/...` приходит как
`PATH_INFO`. Для входа Яндекс выберите методы `GET`, `POST` и `HEAD`: HEAD
проверяет доступность и не запускает `smarthome.php`. Секрет находится в URI,
поэтому он может попасть в access-log nginx
и внешнего reverse proxy; приложение не может удалить его из чужих журналов.
Настройте redaction на прокси или отключите журнал для `/api/hooks/`. Если
внешний proxy закрывает все запросы до PHP, webhook не заработает без исключения
для этой общей ветки.

Схема создаётся миграцией `20261025_api_hooks_v1` и присутствует в
`lib/core/Install/schema.sql`; `dbInstall()` модуля API также вызывает
`Api\Schema::install()`. Не запускайте миграции на рабочей БД для проверки.
Миграция `20261027_api_hook_handlers` идемпотентно добавляет HANDLER_TYPE,
SCRIPT_ID и CODE. Старые записи остаются module. Новая схема установки
содержит эти поля сразу. Миграция не исполняет код и сценарии.

Проверки: `php tests/api_smoke.php`, `php tests/api_http_smoke.php`,
`php tests/api_user_auth_smoke.php` (SQLite: сроки, отзыв, профиль и WS),
`php tests/api_hooks_smoke.php`, `php tests/api_hooks_http_smoke.php`,
`php tests/api_hook_scenarios_smoke.php` (реальный исполнитель сценариев),
обычные routing/config/console/template smoke, PHP lint, node --check и npm run build.
HTTP-фикстуры запускаются только на loopback и не загружают рабочую .env/БД.
