# Быстрый путь MQTT и параллельный core_runtime

## Коротко

Раньше `cycle_mqtt` в одном процессе принимал пакет, писал `mqtt`/`pvalues`/аудит
в MySQL, ставил `ONCHANGE` в `core_runtime` и там же отправлял исходящие команды.
Любая пачка датчиков задерживала и нажатие кнопки, и команду свету. Теперь путь
разделён:

```text
брокер → cycle_mqtt (только приём) → Redis lane queue
                                      ├─ N обработчиков MQTT (порядок по объекту)
                                      ├─ писатель состояния → MySQL (коалесинг)
                                      └─ издатель → брокер (отдельное соединение)

свойство/метод → core_runtime lane queue → N исполнителей (порядок по объекту,
                                            serial — для произвольного PHP)
```

При этом контракт свойств, аудита и журнала автоматизаций не меняется. Меняется
только то, **где** ждём MySQL и пользовательский PHP.

## Когда включается

- Быстрый путь MQTT: `USE_REDIS` задан, расширение `Redis` установлено и
  `MQTT_ASYNC_ENABLED` не равен `0`. Иначе остаётся прежний синхронный путь.
- Параллельный `core_runtime`: `USE_REDIS` задан и `CORE_WORKERS > 1`.
  `CORE_WORKERS=1` возвращает прежний последовательный цикл.

При недоступности Redis приём MQTT падает обратно в синхронную обработку, а
постановка команд — в прямое соединение. Если живы Redis, но обработчики не
подают heartbeat, приём также временно обрабатывает сообщения старым путём,
чтобы очередь не росла бесконечно. Это аварийный режим: он сохраняет
работоспособность, но возвращает MySQL в критический путь.

## Роли процессов

| Процесс | Ответственность |
| --- | --- |
| `scripts/cycle_mqtt.php` | Подключение к брокеру, подписки, фильтры `MQTT_STRIPMODE`/`MQTT_DELAY`, постановка события в Redis. Не пишет `mqtt` и не вызывает пользовательский PHP. |
| `scripts/cycle_mqtt_runtime.php` | Супервизор: держит `MQTT_HANDLERS` обработчиков, писателя состояния и издателя, перезапускает упавших, чинит зависшие аренды. |
| `scripts/mqtt_worker.php handler` | Разбирает JSON, применяет привязки, пишет свойства и ставит автоматизации. |
| `scripts/mqtt_worker.php state` | Переносит накопленные значения и историю в MySQL. |
| `scripts/mqtt_worker.php publisher` | Публикует `mqtt_queue` на отдельном долгоживущем соединении. |
| `scripts/cycle_core.php` | При `CORE_WORKERS > 1` — супервизор исполнителей; при `1` — прежний последовательный цикл. |
| `scripts/core_runtime_worker.php` | Один параллельный исполнитель `core_runtime`. |

`mqtt_worker.php` и `core_runtime_worker.php` — внутренние процессы, их не
запускают вручную. Управление — через `cycles:*`, диагностика — `mqtt:runtime`.

## Очередь с полосами

`lib/core/LaneEventQueue.php` — Redis-очередь с независимыми полосами:

- события одной полосы выполняются строго по порядку;
- разные полосы выполняются параллельно;
- событие лежит в списке до `acknowledge`; после сбоя аренда истекает и
  событие возвращается **в голову** своей полосы (`reap`);
- `acknowledge` проверяет токен аренды: запоздавший ACK не удалит событие,
  которое уже перехватил другой процесс;
- `serial` — эксклюзивная полоса. Пока в ней есть работа, новые объектные
  события не берутся; это защищает произвольный PHP с неизвестными
  зависимостями. Счётчик `serial:pending` не даёт полосе голодать.

Для MQTT полоса — управляемая сущность:

- точная привязка → `object:<LINKED_OBJECT>`;
- JSON-пакет с привязками только к одному объекту → `object:<объект>`;
- несколько объектов или непривязанный топик → `topic:<путь>`.

Для `core_runtime`:

- `method` → `object:<объект метода>`;
- `modulepropertyset` → `object:<объект свойства>`;
- `script`, `api`, `moduleevent`, `subscriptions`, `say*` → `serial`.

Метод считается операцией своего объекта. Если метод управляет другими
объектами, порядок между этими объектами не гарантируется: это и есть
«произвольный PHP с неизвестными зависимостями». Для строгого глобального
порядка используйте сценарий (он идёт в `serial`) или `CORE_WORKERS=1`.

## Кэш привязок

`modules/mqtt/MqttBindingIndex.php` строит снимок `mqtt` одним запросом и
хранит его в Redis по версии:

- точный путь, `PATH_WRITE`, пары «объект.свойство» и все родительские
  префиксы индексируются в памяти;
- редактор привязки вызывает `MqttRuntime::invalidate()` — версия в Redis
  растёт, процессы перечитывают снимок без переподключения к брокеру;
- проверка версии выполняется не чаще двух раз в секунду;
- ведущий `/` — часть топика: `/var/now` и `var/now` различаются;
- снимок сжимается и живёт в Redis час; старые версии истекают сами.

`MqttSchema::ensure()` добавляет индексы `(LINKED_OBJECT, LINKED_PROPERTY)`,
`(LINKED_OBJECT, LINKED_METHOD)`, `(UPDATED)` и `mqtt_history (MQTT_ID, ID)`.
Без них `propertySetHandle()` и история делают полный перебор.

## Проекция состояния

- `mqtt.VALUE/UPDATED` — проекция. В обычном режиме она отстаёт до секунды;
  при большом backlog (много активных топиков, медленный MySQL) отставание
  больше — его показывает `dirty_topics` в `mqtt:runtime`.
- Несвязанная телеметрия объединяется по пути: в MySQL попадает последнее
  значение, а не каждое сообщение.
- Привязанные топики, `LOGGING`, `DEBUG_MODE` и исходящие команды сохраняются
  в `mqtt_history` отдельными событиями. Несвязанная телеметрия без
  `LOGGING`/`DEBUG_MODE` истории не создаёт.
- Список и карточка MQTT накладывают актуальные значения из Redis
  (`MqttRuntime::overlay()`), поэтому секундное отставание не видно в UI.
- Поиск/сортировка по `VALUE` в SQL и внешние SQL-читатели видят проекцию, а
  не последнее значение. Это осознанный компромисс.

Удаление топика вызывает `MqttRuntime::forget()`, чтобы отложенная запись не
воскресила строку.

## Публикация

При быстром пути `mqttPublish()` всегда ставит команду в `mqtt_queue`, даже
если в настройках выбран прямой способ. Издатель держит одно соединение и
забирает очередь пачками; автоматизация не ждёт TCP-соединения и не
конкурирует с приёмом датчиков. При `MQTT_WRITE_METHOD=0` старый прямой путь
остаётся только аварийным fallback.

## Сбои и диагностика

- Аренда обработчика — `MQTT_HANDLER_LEASE` (по умолчанию 120 с). Зависшие
  события возвращает супервизор каждые 5 секунд.
- Ошибка обработки повторяется с задержкой 2, 4, 8… секунд
  (`MQTT_MAX_ATTEMPTS`, по умолчанию 5), затем событие уходит в
  `failed`-журнал, а не теряется молча.
- Ошибки состояния/истории повторяются писателем; после трёх попыток событие
  истории отбрасывается с записью в журнал.
- Каждый обработчик, писатель состояния и издатель оставляют heartbeat в Redis.
  Если процесс жив, но завис в SQL/брокере, супервизор перезапускает только эту
  роль, не дожидаясь watchdog всего цикла.
- Замеры `intake`, `claim`, `handle`, `property`, `publish`, `project`
  хранятся в Redis (последние 100 значений): count, avg, p95, last.
- `php majordomo mqtt:runtime` показывает очереди, счётчики, задержки и
  последние неудачные события.
- `php majordomo mqtt:runtime --reap` возвращает зависшие события;
  `--flush` принудительно переносит состояние и историю; `--failed` показывает
  журнал неудачных событий.

## Настройки

В админке: «Общие настройки» → «MQTT и очередь». `CORE_WORKERS` — там же,
в «Производительности». В настройках самого модуля MQTT эти ключи не
редактируются: модуль хранит параметры брокера, а очередь и процессы — в `.env`.

| Ключ | По умолчанию | Смысл |
| --- | --- | --- |
| `MQTT_ASYNC_ENABLED` | `1` | Выключатель быстрого пути при наличии Redis |
| `MQTT_HANDLERS` | `3` | Число параллельных обработчиков MQTT |
| `MQTT_HANDLER_LEASE` | `120` | Аренда события, секунды |
| `MQTT_MAX_ATTEMPTS` | `5` | Повторы перед failed-журналом |
| `CORE_WORKERS` | `3` | Параллельные исполнители core_runtime; `1` — старый режим |

## Ограничения

- Redis обязателен для быстрого пути. Нужны persistence и `maxmemory-policy
  noeviction`: очередь нельзя вытеснять как кэш. Код не меняет настройки Redis.
- Порядок гарантируется внутри полосы, не между полосами.
- `moduleevent` и сценарии остаются в `serial`: модуль может затрагивать любые
  объекты, автоматически доказать независимость нельзя.
- Каждый обработчик держит снимок привязок в памяти. На очень больших таблицах
  уменьшайте `MQTT_HANDLERS`; снимок перечитывается только при смене версии.
- `mqtt`-таблица — проекция; не используйте её как источник «последнего
  значения» в новых внешних интеграциях, читайте API/свойства.
- Это не exactly-once: после сбоя обработчика возможен повтор уже выполненных
  действий. Обработчики внешних команд должны быть идемпотентны.

## Проверки

```bash
php tests/mqtt_throttle_smoke.php
php tests/mqtt_binding_index_smoke.php
$env:MJD_TEST_REDIS_PORT='<port>'; php tests/lane_queue_smoke.php
$env:MJD_TEST_REDIS_PORT='<port>'; php tests/core_lanes_smoke.php
$env:MJD_TEST_REDIS_PORT='<port>'; php tests/mqtt_runtime_smoke.php
$env:MJD_TEST_REDIS_PORT='<port>'; php tests/mqtt_runtime_processing_smoke.php
php tests/console_smoke.php
```

Тесты с Redis используют одноразовую базу и уникальный префикс, не вызывают
`FLUSHDB` и не трогают рабочую очередь.
