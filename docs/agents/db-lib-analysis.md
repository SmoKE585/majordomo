## Безопасно исправлено

### `SQLExec()` и пустой запрос

Файл: `lib/sqlFunctions.class.php`.

Проблема: `SQLExec()` проверял `$query[0]` до проверки пустой строки. На PHP 8 это может давать предупреждение при пустом запросе. Исправление не меняет SQL-логику: пустой, `null` и `false` запросы по-прежнему не выполняются, но первый символ читается только после этой проверки.

## Найденные проблемы и риски, которые не исправлялись

Эти пункты не менялись специально, потому что без профилирования, схемы конкретной установки или end-to-end проверки легко сломать совместимость старых модулей.

### 1. N+1 в `getObjectsByProperty()`

Файл: `lib/objects.class.php`, функция `getObjectsByProperty()`.

Сначала выбираются все свойства с нужным `TITLE`, затем для каждого свойства отдельным запросом выбираются `pvalues` и `objects`. Это классический N+1. Теоретически можно заменить на один `JOIN` по `properties`, `pvalues`, `objects`, но нужно аккуратно сохранить логику сравнения значений в PHP, особенно строковые/числовые сравнения и дубликаты объектов.

Рекомендация: оптимизировать только после замера на реальных данных. Безопасный путь: написать отдельный тест на все операторы условия (`=`, `==`, `>`, `>=`, `<`, `<=`, `<>`, `!=`) и только потом объединять запросы.

### 2. Рекурсивные запросы в `getObjectsByClass()` и `getClassProperties()`

Файл: `lib/objects.class.php`, функции `getObjectsByClass()` и `getClassProperties()`.

Обе функции обходят иерархию классов рекурсивно и на каждом уровне делают новые SQL-запросы. На глубокой или широкой иерархии это может быть дорого. В `getClassProperties()` есть кеш по `$class_id`, но он локален для процесса и не решает полный N+1 при первом проходе.

Рекомендация: не переписывать в один запрос без проверки наследования. Более безопасный вариант для будущего: сначала добавить измерения времени/количества запросов, затем кэшировать карту `classes` и `properties` внутри одного вызова.

### 3. N+1 при чистке истории свойств

Файл: `lib/objects.class.php`, функция `cleanUpPropertyHistory()`.

Функция выбирает все `pvalues` для свойства и для каждого значения вызывает `cleanUpValueHistory()`, где идут отдельные операции по таблицам истории. Это может быть тяжелым на больших историях.

Риск исправления: таблица истории может быть не только `phistory`, но и архивная таблица по году/месяцу. Массовое объединение запросов может удалить не те данные или изменить подсчет удаленных строк.

Рекомендация: сначала собрать статистику по объемам `phistory` и архивных таблиц, затем оптимизировать отдельным сценарием обслуживания, не в общем ядре.

### 4. Запрос в цикле при смене класса объекта

Файл: `lib/objects.class.php`, функция `objectClassChanged()`.

На втором этапе для каждого свойства нового класса выполняется отдельный `SQLSelectOne()` для поиска объектного свойства с таким же названием. Это N+1.

Риск исправления: функция меняет структуру свойств объекта и удаляет старые записи из `properties`. Ошибка здесь может привести к потере связей свойств.

Рекомендация: если оптимизировать, сначала добавить транзакционный сценарий или хотя бы тестовую фикстуру объекта со сменой класса, совпадающими и несовпадающими свойствами.

### 5. Двойная обработка SQL-ошибок в `Select()` и `SelectOne()`

Файлы: `lib/mysqli.class.php` и `lib/mysql.class.php`.

`Exec()` уже вызывает `Error()` при ошибке запроса, а затем `Select()`/`SelectOne()` при `false` вызывают `Error()` повторно. Это может давать дубли в логах и повторное создание `custom_error`.

Почему не исправлено: изменение может повлиять на старую диагностику и сценарии, которые косвенно зависят от текущего поведения ошибок.

Рекомендация: менять только отдельной задачей, после проверки типичных ошибок `SELECT`, `SHOW`, ошибок синтаксиса и отсутствующих колонок.

### 6. Неэкранированные имена таблиц и полей в helper-функциях

Файл: `lib/sqlFunctions.class.php`.

Функции `SQLTruncateTable()`, `SQLDropTable()`, `SQLGetFields()`, `SQLGetIndexes()` напрямую вставляют имя таблицы в SQL. В других местах динамические имена таблиц тоже собираются строками, например история свойств в `lib/objects.class.php` и `lib/caching.class.php`.

Почему не исправлено: простое добавление `DBSafe()` для идентификаторов не равно безопасному экранированию SQL identifier. Для таблиц и полей нужен отдельный whitelist/validator вроде `^[A-Za-z0-9_]+$`, но такое изменение может сломать нестандартные имена таблиц сторонних модулей.

Рекомендация: ввести отдельную функцию безопасной проверки SQL-идентификаторов и сначала применить ее только к новым/служебным вызовам, не ко всему ядру сразу.

### 7. Команды дампа и восстановления БД собираются строкой

Файл: `lib/sqlFunctions.class.php`, функции `SQLMakeDBDump()`, `SQLMakeTableDump()`, `SQLRestoreDBDump()`.

Параметры командной строки собираются конкатенацией: путь к утилите, host, user, password, имя БД, имя таблицы и путь к файлу. Это риск для путей с пробелами, спецсимволов и потенциальной command injection, если в параметры попадут внешние данные.

Почему не исправлено: корректное исправление для Windows и Linux требует аккуратного `escapeshellarg()`/разделения редиректа, а также проверки `PATH_TO_MYSQLDUMP`, `SERVER_ROOT` и restore через `<`. Небольшая правка может сломать backup/restore на части установок.

Рекомендация: вынести backup/restore в отдельную задачу и проверить на Windows и Linux. Для восстановления лучше использовать `proc_open()` или передачу файла через stdin, а не строковый `<`.

### 8. `lib/db.class.php` на PDO почти не используется

Файл: `lib/db.class.php`.

Поиск по репозиторию показал только внутренний вызов `DB::lastInsertId()` внутри самого файла. В обычной цепочке загрузки `lib/loader.php` файл все равно подключается, но основное ядро работает через глобальный `$db` и функции `SQL*`.

Почему не помечено deprecated: файл подключается общим загрузчиком библиотек и может использоваться сторонними модулями динамически, даже если ссылок в репозитории нет.

Рекомендация: не удалять и не помечать deprecated без проверки внешних модулей. Если развивать PDO-слой, нужно сначала определить единый API и правила сосуществования с `SQLSelect`/`SQLExec`.

### 9. Непоследовательная обработка `NULL` в INSERT/UPDATE

Файлы: `lib/mysqli.class.php` и `lib/mysql.class.php`.

В `lib/mysqli.class.php` метод `Update()` пишет SQL `NULL` для `null`, а `Insert()` превращает `null` в пустую строку через `(string)$value`. В старом `lib/mysql.class.php` и `Update()`, и `Insert()` фактически превращают `null` в пустую строку.

Почему не исправлено: изменение `Insert()` на настоящий SQL `NULL` может поменять данные, дефолты и совместимость модулей, которые привыкли к пустым строкам.

Рекомендация: оставить как есть до отдельной миграционной задачи. Если менять, делать это таблица-за-таблицей.

### 10. Риск гонок в очереди jobs

Файл: `lib/common.class.php`, блок обработки `jobs` около запросов `PROCESSED=0` и `STARTED`.

Код выбирает пачку jobs, затем для каждой делает `UPDATE STARTED`, затем отдельным `SELECT` проверяет, удалось ли забрать job. Это не N+1 в чистом виде, а ручная optimistic-lock схема.

Почему не исправлено: простая замена на один массовый `UPDATE` или транзакцию может изменить конкуренцию между несколькими процессами.

Рекомендация: если оптимизировать, сначала описать модель конкуренции циклов и проверить на нескольких параллельных worker-процессах.

## Дополнение по аварийному выключению питания

После дополнительной проверки найдено, что базовая схема `docs/dev/db_terminal.sql` содержит 35 таблиц `ENGINE=MyISAM`, 4 таблицы `ENGINE=InnoDB` и 3 таблицы `ENGINE=MEMORY`. Для сценария резкого выключения питания это критично: MyISAM не журналирует изменения как InnoDB и существенно чаще требует `CHECK/REPAIR TABLE` после падения питания или процесса MySQL.

### Что исправлено в maintenance

Файл: `scripts/startup_maintenance.php`.

Старый блок проверки таблиц был ненадежным: он вызывал `SQLExec("CHECK TABLE ...")` и считал таблицу исправной по факту возврата result set. Для `CHECK TABLE` это некорректно, потому что результат запроса может быть успешным, а реальный статус лежит в поле `Msg_text` и может быть не `OK`.

Теперь startup maintenance:

- берет список таблиц из `information_schema.tables`;
- пропускает `MEMORY`-таблицы;
- выполняет `CHECK TABLE` через `SQLSelectOne()`;
- считает таблицу исправной только если `Msg_text = OK`;
- для MyISAM пробует `REPAIR TABLE`, затем `REPAIR TABLE ... EXTENDED`, затем `REPAIR TABLE ... USE_FRM`;
- не пытается делать `REPAIR TABLE` для не-MyISAM движков, потому что для InnoDB это не штатный способ восстановления;
- использует строгую проверку SQL-идентификаторов для имен таблиц в maintenance.

Это не гарантирует восстановление любой таблицы. Если повреждены `.frm`/структура, если диск вернул битые данные, или если MySQL не может открыть таблицу вообще, нужен backup или ручное восстановление.

### Что нужно планировать отдельно

Главная долгосрочная мера: постепенно переводить критичные таблицы с MyISAM на InnoDB. Массово делать `ALTER TABLE ... ENGINE=InnoDB` из ядра небезопасно: нужно проверить индексы, размеры таблиц, блокировки, версию MySQL/MariaDB и поведение сторонних модулей.

Разумный порядок:

1. Сначала перевести новые установки на InnoDB в `docs/dev/db_terminal.sql`, если нет обратных несовместимостей.
2. Для существующих установок добавить отдельный ручной maintenance-инструмент: показать MyISAM-таблицы, размер, строки, оценку риска и кнопку/команду конвертации по одной таблице.
3. Начинать с небольших и критичных справочников (`settings`, `objects`, `properties`, `pvalues`, `jobs`), а большие исторические таблицы (`phistory`, `history`, архивы `phistory_value_*`) переносить только в maintenance window.
4. Перед конвертацией обязательно делать backup и проверять свободное место на диске: `ALTER TABLE ... ENGINE=InnoDB` может временно требовать сопоставимый объем места.

### Эксплуатационная рекомендация

Для реальной защиты от отключения питания кодом это полностью не решается. Минимальный практичный набор:

- UPS для сервера или хоста с MySQL/MariaDB;
- включенный автозапуск `cycle.php`, чтобы startup repair выполнялся до основной работы;
- регулярный backup на отдельный носитель;
- по возможности перевод MyISAM-таблиц на InnoDB после теста на конкретной установке.

## Статус правок по пунктам 1-4

Дата правок: 2026-06-06.

### 1. `getObjectsByProperty()`

Файл: `lib/objects.class.php`.

Исправлено: убран N+1 по `properties -> pvalues`. Вместо выбора `properties` и отдельного запроса `pvalues` для каждого свойства теперь используется один `JOIN` по `properties`, `pvalues`, `objects`.

Сохранены важные детали старого поведения:

- если свойства с таким названием нет, возвращается `0`;
- если свойство есть, но значений `pvalues` нет, возвращается пустой массив;
- сравнения значений остались в PHP и используют те же операторы, чтобы не менять строковую/числовую семантику MySQL/PHP;
- результат по-прежнему возвращает массив названий объектов без дублей.

### 2. `getObjectsByClass()` и `getClassProperties()`

Файл: `lib/objects.class.php`.

`getObjectsByClass()` больше не вызывает саму себя с SQL-запросами на каждом уровне дерева. Теперь функция:

- как раньше находит стартовый класс тем же SQL-условием;
- одним запросом загружает карту классов;
- в памяти собирает список дочерних классов;
- одним запросом выбирает объекты по всем найденным `CLASS_ID`;
- возвращает только `ID` и `TITLE`, как раньше.

Добавлена защита от циклов в дереве классов, чтобы поврежденная иерархия не приводила к бесконечной рекурсии.

`getClassProperties()` для обычного вызова без `$def` теперь собирает цепочку родителей через карту классов и одним запросом получает свойства по всем классам цепочки. Внешний формат результата сохранен. Ветка с `$def` оставлена в старой логике, потому что она используется как внутренний фильтр наследования и менять ее рискованнее.

### 3. `cleanUpPropertyHistory()`

Файл: `lib/objects.class.php`.

Сделана только безопасная часть:

- запрос `pvalues` теперь выбирает только `ID`, а не `SELECT *`;
- `PROPERTY_ID` приводится к `(int)` в SQL.

Полное устранение N+1 здесь не сделано намеренно. `cleanUpValueHistory()` зависит от режима `SEPARATE_HISTORY_STORAGE`, может работать с разными таблицами истории и при `DATA_TYPE=5` удаляет файлы из `cms/images`. Массовое объединение удаления без отдельной проверки может сломать подсчет удаленных файлов или удалить не те данные.

### 4. `objectClassChanged()`

Файл: `lib/objects.class.php`.

Исправлено: на втором этапе смены класса больше нет отдельного `SQLSelectOne()` на каждое свойство нового класса. Теперь объектные свойства с совпадающими названиями выбираются одним запросом и складываются в карту `TITLE -> pvalue`.

Сохранено старое поведение:

- первый найденный объектный property с нужным `TITLE` используется как раньше;
- `SQLUpdate('pvalues', ...)` получает только поля `pvalues`, служебный `PROPERTY_TITLE` удаляется перед update;
- удаление старого object-level свойства осталось тем же `DELETE FROM properties WHERE ID=...`.

## Статус правок по пунктам 5, 7 и 10

Дата правок: 2026-06-06.

### 5. Двойная обработка SQL-ошибок

Файлы:

- `lib/mysqli.class.php`
- `lib/mysql.class.php`

Исправлено: `Select()` и `SelectOne()` больше не вызывают `Error()` повторно, если `Exec()` вернул ошибку. Ошибка по-прежнему обрабатывается в `Exec()` при `$ignore_errors = false`, поэтому логирование и `custom_error` остаются, но без дублей.

Дополнительно добавлен метод `AffectedRows()` в оба драйвера. Он нужен для стабильного claim jobs в пункте 10.

### 7. Backup/restore БД без shell-конкатенации

Файл: `lib/sqlFunctions.class.php`.

Исправлено: `SQLMakeDBDump()`, `SQLMakeTableDump()` и `SQLRestoreDBDump()` больше не собирают shell-команду строковой конкатенацией с `>` и `<`.

Теперь используется `proc_open()` с массивом аргументов:

- `mysqldump` получает аргументы отдельными элементами массива;
- dump пишет stdout сразу во временный файл через descriptor;
- restore читает dump через stdin descriptor;
- stderr/stdout собираются в `$output` для логирования;
- успешный dump требует `exit code = 0` и непустой `.tmp` файл;
- неуспешный `.tmp` удаляется, чтобы не принять частичный dump за рабочий backup;
- добавлена поддержка `PATH_TO_MYSQL` для mysql-клиента, аналогично существующему `PATH_TO_MYSQLDUMP`.

Ограничение проверки: проверен запуск внешней команды через `SQLRunExternalCommand()` на текущей PHP-сборке. Реальный `mysqldump/mysql restore` не запускался, потому что это требует рабочей БД и безопасного тестового dump-файла.

### 10. Стабильный claim scheduled jobs

Файлы:

- `lib/common.class.php`
- `lib/sqlFunctions.class.php`
- `lib/mysqli.class.php`
- `lib/mysql.class.php`

Исправлено: `runScheduledJobs()` больше не подтверждает claim через повторный `SELECT` по `STARTED` без проверки, изменила ли текущая попытка строку.

Новая схема:

1. Выбирается список кандидатов как раньше.
2. Для каждого job выполняется атомарный `UPDATE jobs SET STARTED=... WHERE ...` с полным условием актуальности: `PROCESSED=0`, `EXPIRED=0`, `RUNTIME <= now`, `STARTED IS NULL OR STARTED <= stale`.
3. Job выполняется только если `SQLAffectedRows() > 0`.
4. После успешного claim данные job перечитываются из БД.
5. При ошибке выполнения job сбрасывается только если `STARTED` совпадает с текущим claim-временем.
6. `PROCESSED=1` выставляется также с проверкой текущего `STARTED` и `PROCESSED=0`.

Это устраняет гонку, при которой два процесса в одну секунду могли оба увидеть одинаковый `STARTED` и выполнить один job дважды.

- HTTP endpoint `/objects/?system_call=1&job=...` в `objects/index.php`;
- ручной модуль jobs в `modules/jobs/jobs.class.php`.

### Найденные причины нестабильного выполнения

1. `setTimeOut()` раньше создавал job через `addScheduledJob()` с дефолтным `expire = 1800` секунд. Если сервер был выключен, цикл не работал, время на системе прыгнуло вперед или job не дошел до выполнения за 30 минут после `RUNTIME`, запись удалялась строкой `DELETE FROM jobs WHERE EXPIRE <= now` до исполнения.

2. `runScheduledJobs()` выполнял команду через HTTP-вызов `getURL(BASE_URL . '/objects/?system_call=1&job=...')`. Общий `getURL()` имеет `CURLOPT_TIMEOUT = 45`, поэтому долгие отложенные команды могли не дождаться ответа и считаться ошибочными.

3. `objects/index.php` ловил только `Exception`, но не `Throwable`. Ошибки уровня `ParseError`, `TypeError` и другие PHP 7/8 Throwable могли не регистрироваться как ошибка scheduled job.

### Что исправлено

Файлы:

- `lib/common.class.php`
- `objects/index.php`

Изменения:

- `setTimeOut()` теперь вызывает `addScheduledJob(..., $expire = 0)`, то есть новые таймеры не получают автоматическое истечение через 30 минут;
- `addScheduledJob()` теперь не пишет `EXPIRE`, если `$expire <= 0`, и оставляет `EXPIRE = NULL`;
- для прямых вызовов `addScheduledJob()` старый дефолт `1800` сохранен, чтобы не менять чужую явную семантику;
- `runScheduledJobs()` теперь передает в `getURL()` отдельный timeout для jobs: `JOBS_EXECUTION_TIMEOUT`, по умолчанию 300 секунд;
- `objects/index.php` теперь ловит `Throwable` при выполнении scheduled job.

### Что не менялось намеренно

Полностью убирать HTTP-вызов и выполнять `eval()` прямо внутри `runScheduledJobs()` рискованно: `eval()` внутри функции меняет область видимости PHP-кода. Сейчас job-код выполняется в `objects/index.php` на верхнем уровне, и часть старых пользовательских команд может неявно зависеть от такой области видимости.

Если потом делать локальное выполнение без HTTP, нужно сначала вынести исполнение в отдельный runner с совместимой областью видимости или проверить реальные пользовательские сценарии.
