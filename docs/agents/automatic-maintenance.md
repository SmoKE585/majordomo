# Автоматическое обслуживание

С 11.11.2026 `cycle_main` не запускает старое полное обслуживание.
Супервизор сам обнаруживает `cycle_maintenance` среди `scripts/cycle_*.php`.
Отдельный cron или systemd timer не требуется. При обновлении нужно
перезапустить супервизор и циклы, чтобы работал новый порядок запуска.

## Расписание

- `cleanup` — каждые 900 секунд: аудит с бюджетом четыре секунды, по тысяче
  просроченных событий и записей ошибок за запуск. Сохраняются последние тысяча
  событий даже при пропусках в ID. Историей значений продолжает заниматься
  существующий HistoryWriter по настройкам свойств.
- После 04:00 по часовому поясу установки — `backup`, `files`, `tables`.
  Завершённые этапы не повторяются в тот же день после перезапуска.
  Пропущенный ночной запуск выполняется после включения системы, если 04:00 уже прошло.
- Ошибочный этап повторяется с паузами 5 и 10 минут, максимум три попытки за
  период. Другие этапы продолжаются. На следующий день попытки ночного этапа
  начинаются заново. Очистка получает новый период каждые 15 минут.

Настройки из Config: `MAINTENANCE_HOUR=4`, `MAINTENANCE_INTERVAL=900`,
`MAINTENANCE_TIMEOUT=1800` секунд для резервного копирования. Другие этапы имеют
предел 60 секунд для cleanup и 300 секунд для файлов и таблиц. Родитель обновляет
heartbeat, пока работает отдельная CLI-команда. Таймаут завершает её группу
процессов, включая внешний mysqldump. Процессы и сигналы проверяются в Linux.

Результаты и попытки хранятся в `cms/cycles/maintenance/automatic.json`.
Блокировки ОС предотвращают два планировщика и две операции одновременно;
при аварии владельца они освобождаются. Старые циклы `cycle_db_save` и
`cycle_periodical_db_save`, если установлены, используют то же расписание и
блокировку через адаптер `periodical_db_save.php`. Их прежние индивидуальные
интервалы резервирования заменены общим расписанием 04:00.

## Копии и ремонт

Копии размещаются в `SETTINGS_BACKUP_PATH/automatic/ГГГГММДД`, по умолчанию
`backup/automatic/ГГГГММДД`. Сохраняются SQL-дамп и пользовательские данные CMS;
кэши, журналы, скачанные обновления и состояние процессов пропускаются.
Символические ссылки не обходятся. Файлы дампа имеют права 0600, каталоги — 0700.
Параметры подключения передаются mysqldump через временный файл 0600, а не пароль
в аргументах. После дампа и копирования создаётся `complete.json`; неполная копия
не считается успешной и не разрешает ремонт.

Дамп использует `--single-transaction --quick --skip-lock-tables`: InnoDB получает
транзакционный снимок без удержания общей read-lock на всё время копирования
большого аудита. **Для изменяемых MyISAM-таблиц общей транзакционной согласованности
нет.** Для гарантированного согласованного снимка такой базы требуется отдельное
окно остановки записей. Автообслуживание этого окна не создаёт.

Ночная проверка выполняет только `CHECK TABLE ... QUICK` для MyISAM. Полные
проверки InnoDB, включая большой `property_audit_events`, не выполняются при
каждом запуске. Если MyISAM повреждена и имеется завершённая копия не старше
семи дней, применяется обычный `REPAIR TABLE` и повторная проверка. `EXTENDED`,
`USE_FRM`, удаление/пересоздание таблиц и ремонт InnoDB не автоматизируются.
Отсутствие копии или неудача ремонта сохраняются как ошибка этапа.

Старые журналы удаляются по `LOG_FILES_EXPIRE`, корневой каталог сохраняется.
Просроченные полные и неполные копии удаляются по `BACKUP_FILES_EXPIRE` только
в управляемом подкаталоге `automatic`, после проверки границ пути. Старые
пользовательские каталоги резервирования вне `automatic` не затрагиваются.
Текущие картинки не удаляются на основании отсутствия картинки в истории;
старый опасный проход исключён. Часы не «исправляются» удалением данных.
Структурные изменения и объединение старых строк выполняются миграциями,
а не на каждом старте.

## Готовность main

`WAIT_FOR_MAIN_CYCLE=1` включён по умолчанию. Сначала стартует main, готовит
служебные значения и ставит `ThisComputer.StartUp` и startup в очередь. Затем
создаёт `cms/cycles/main.ready.json` со своим PID. Только после этого супервизор
запускает остальные циклы, включая WebSocket и обслуживание. Завершение всех
пользовательских startup-обработчиков не является условием готовности ядра.

Перед каждым новым запуском main маркер удаляется; PID сверяется с живым
процессом супервизора. Ожидание не запускает дочерний процесс и не расходует
попытки восстановления. Уже работающие дочерние циклы при отдельном рестарте
main не останавливаются. Явный `WAIT_FOR_MAIN_CYCLE=0` отключает ожидание.
Сохранённые ранее окончательные ошибки циклов автоматически не стираются:
после устранения причины такой цикл запускается штатной командой `cycles:start`.

## CLI

```bash
php majordomo maintenance:run --status --json
php majordomo maintenance:run
php majordomo maintenance:run --force
php majordomo maintenance:run --task=cleanup --json
php majordomo maintenance:run --task=tables
```

Без опций выполняются только этапы, которым пришло время. `--force` запускает
все четыре этапа сразу. `--task` выполняет отдельную операцию под общей блокировкой;
`--status` не подключается к БД. Старый `scripts/startup_maintenance.php` оставлен
адаптером полного ручного запуска; внутри старого main с `run_from_start=1` он
не выполняет тяжёлых операций. Команды режима обслуживания `maintenance:on/off/status`
сохраняют прежний смысл и не являются этой очисткой.
Операции CLI выполняются от пользователя службы, чтобы приватные резервные
копии оставались доступны последующим автоматическим запускам.

Проверки: `php tests/automatic_maintenance_smoke.php`,
`php tests/cycle_startup_smoke.php`, `php tests/console_smoke.php`.
Процессы и сигналы дополнительно проверяются в изолированном Linux-контейнере.
