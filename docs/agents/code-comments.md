# Комментарии в коде и история изменений

Коротко: комментарии пишутся по-русски и объясняют человеку смысл, а не
пересказывают синтаксис. При изменении кода класса в его заголовок добавляется
запись `ГГГГ-ММ-ДД — что изменилось`. Это правило для всех агентов и
контрибьюторов; оно проверяется на ревью вместе с тестами.

## 1. Зачем это нужно

Код читают не только авторы. Администратор открывает модуль, чтобы понять,
почему устройство ведёт себя так, а не иначе; агент — чтобы не сломать
неочевидное поведение. Хороший комментарий отвечает на вопросы:

- **что** делает этот блок или класс;
- **почему** сделано именно так (ограничение, совместимость, защита);
- **что произойдёт**, если это убрать или изменить.

Плохой комментарий повторяет код и ничего не добавляет.

## 2. Правила комментариев

1. **По-русски.** Новые комментарии — на русском. Имена классов, методов,
   файлов, ключей и API остаются как есть.
2. **Смысл, а не синтаксис.** Пишите «почему», если код неочевиден.
3. **Близко к коду.** Комментарий стоит перед блоком, к которому относится, а
   не в конце файла.
4. **Коротко.** Одна-три строки на блок. Большое объяснение — в заголовок
   класса или в документацию.
5. **Для человека.** Расшифровывайте аббревиатуры и «магические» числа.
6. **Не устаревать.** Меняете поведение — обновите комментарий рядом.

Хорошо:

```php
// Модуль уже получил это значение в текущей цепочке. Второй раз не
// уведомляем: иначе автоматизация A → модуль → A зациклится.
if (in_array($token, $chain, true)) {
    return;
}
```

```php
// 32 шага — предохранитель от длинных цепочек. Значение сохраняем,
// но дальше по цепочке не идём.
if (count($chain) >= PropertyChain::MAX_LENGTH) {
```

Плохо:

```php
// Увеличиваем i на 1
$i++;
```

```php
// Проверка
if ($value === false) { ... }
```

## 3. Заголовок класса и история изменений

У каждого класса — короткий docblock: что это, зачем и какую роль играет.
Под ним — блок «Изменения» с датами. Новые записи добавляются **сверху**.

```php
/**
 * Запись и чтение свойств объектов.
 *
 * Сохраняет значение, ведёт историю и аудит, вызывает ONCHANGE и ставит
 * уведомления привязанным модулям. Цепочка изменений защищает от циклов.
 *
 * Изменения:
 * 2026-10-22 — сообщение о цикле объясняет причину и что делать.
 * 2026-10-18 — добавлена проверка повтора свойства в цепочке.
 */
final class Properties
{
```

Правила:

- дата в формате `ГГГГ-ММ-ДД` (например, `2026-10-22`);
- запись добавляется, если менялся **код класса**, а не только комментарий;
- формулировка — что изменилось для поведения, а не «правки»;
- старые записи не удаляются и не переписываются;
- если классов в файле несколько, история — у главного класса файла.

Для файлов без класса (`*.inc.php`, скрипты, миграции) — короткий заголовок
файла:

```php
<?php
// 2026-10-22 — описание ошибки подставляется из ErrorCatalog, чтобы группа
// не оставалась без объяснения. См. docs/agents/errors.md.
```

## 4. Комментарии к методам

Для публичных методов достаточно одной строки: что делает и что возвращает.
Параметры и исключения описывайте, если это неочевидно.

```php
/**
 * Возвращает описание кода ошибки для журнала.
 *
 * @return array{TITLE:string,DETAILS:string}
 */
public static function get(string $code): array
```

Не нужно дублировать типы из сигнатуры — PHP 8.1 их и так показывает.

## 5. Чего избегать

- комментариев-«шума» (`// цикл`, `// конец`);
- английских комментариев в новом коде;
- комментариев, которые противоречат коду;
- «TODO» без имени и даты — лучше задача в трекере;
- пересказа очевидного вместо объяснения причины.

## 6. Чек-лист перед сдачей

- [ ] у нового/изменённого класса есть заголовок: что это и зачем;
- [ ] в заголовке есть запись `ГГГГ-ММ-ДД — что изменилось`;
- [ ] неочевидные ветки и защиты объяснены по-русски;
- [ ] комментарии не повторяют код и не противоречат ему;
- [ ] в модуле/классе нет новых английских комментариев;
- [ ] если менялось поведение — обновлены комментарий и документация.
