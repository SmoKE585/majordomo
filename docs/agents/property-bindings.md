# Свойства, ONCHANGE и подписки модулей

## Коротко

Как свойство сохраняется, как вызывается `ONCHANGE` и как привязанный модуль получает значение. Читайте перед изменением записи свойств, `LINKED_MODULES` или обработчика `propertySetHandle()`.

Документ описывает обе стороны одной цепочки:

1. изменение свойства объектом или модулем → проверка → запись → история/WebSocket →
   `ONCHANGE` → уведомление привязанных модулей;
2. изменение свойства устройством → привязанный модуль получает значение и
   применяет его к своему оборудованию.

## 1. Где что лежит

| Слой | Файл |
| --- | --- |
| Публичные функции `gg/sg/getGlobal/setGlobal/callMethod/callMethodSafe` | `lib/core/Helpers/Objects.php`; старое подключение — `lib/objects.class.php` |
| Публичные функции привязок модулей | `lib/core/Helpers/PropertyBindings.php` |
| Запись/чтение свойств, `ONCHANGE`, постановка уведомлений | `lib/core/Properties.php` |
| Разрешение объекта, свойства и строки значения | `lib/core/Objects.php` |
| Подписки `pvalues.LINKED_MODULES` | `lib/core/PropertyBindings.php` |
| Очередь фоновых операций | `lib/core/OperationsQueue.php`, `lib/core/ApiClient.php` |
| Выполнение уведомлений модулей | `lib/core/OperationWorker.php`, `scripts/cycle_core.php` |
| Журнал системных событий (отдельный механизм) | `lib/core/Events/EventBus.php` |

`EventBus` — это подписка на события системы (`MODULE_INSTALLED`,
`SYSTEM_UPDATED`, …), а не на свойства. Не смешивайте её с
`subscribeToEvent()`/`processSubscription()`.

## 2. Запись свойства

```
setGlobal('Lamp.status', 1, array('mqtt' => 0), 'zigbee')
  → Objects::setValue()
    → Properties::set()
      1. нормализация значения и источника (массив → JSON, null → '')
      2. необязательный лог TRACK_DATA_CHANGES в .data
      3. PropertyLock по (OBJECT_ID, PROPERTY) — сериализация записи одного свойства
      4. resolve свойства: объекта → класса → родительских классов
      5. валидация свойства (число/да/список/код)
      6. чтение старого значения, UPDATE/INSERT pvalues.VALUE, SOURCE, UPDATED
      7. cache; при фактическом изменении значения — property_audit
      8. WebSocket (если значение изменилось) → phistory_queue (если KEEP_HISTORY)
      9. проверка _chain: повтор свойства или 32 шага → property_chain,
         дальнейшие уведомления и ONCHANGE для шага не ставятся
     10. для каждого токена LINKED_MODULES:
             ApiClient → OperationsQueue('modulepropertyset')
     11. ONCHANGE (если цепочка не остановлена):
             raiseEvent → OperationsQueue (web и CLI одинаково)
```

Важные детали:

- Строка значения ищется по `(PROPERTY_ID, OBJECT_ID)`, а не по
  `PROPERTY_NAME`. Старое имя может остаться у переопределённого/унаследованного
  свойства и указывать на «мёртвую» строку. Это касается и чтения: `Properties::get()`
  сначала разрешает активное свойство и только потом использует `PROPERTY_NAME`
  как fallback для легаси-строк.
- `no_linked`:
  - массив `array('mqtt' => 0)` — исключить только перечисленные модули;
  - `1` — не уведомлять привязанные модули; при наличии `LINKED_MODULES`
    легаси-поведение дополнительно пропускает WebSocket/историю/`ONCHANGE`
    (ранний `return`). Не используйте `1`, если нужен `ONCHANGE`.
- `ONCHANGE` вызывается и при повторной записи того же значения. Теперь он
  всегда уходит в очередь: web-запрос не ждёт пользовательский метод, а
  поведение web и CLI совпадает.
- Каждая доставка несёт цепочку `_chain` (последние посещённые свойства). Если
  свойство в цепочке повторяется, значение сохраняется, но новые уведомления и
  `ONCHANGE` для него не ставятся — это обрыв цикла `A → B → A`.
- Вместе с `_chain` через очередь идёт `_trace` — идентификатор запуска для
  always-on журнала [`property-audit.md`](property-audit.md). Он не участвует в
  защите от циклов: `PropertyChain` по-прежнему проверяет только свойства.
- Модуль, который сейчас обрабатывает уведомление, автоматически исключается из
  своих же уведомлений (`PropertyChain::source()`), даже если он не передал
  `no_linked`.
- Уведомления модулей ставятся в очередь **до** `ONCHANGE`. Если постановка в
  очередь падает, значение уже сохранено; ошибка не ломает вызывающий код, а
  показывается один раз за окно через `ErrorReporter` (код `property_delivery`).
  Для старого строгого поведения есть `PROPERTY_DELIVERY_STRICT=true`.

## 3. Доставка привязанному модулю

`OperationsQueue` хранит операцию `modulepropertyset` с параметрами
`object/property/value` и служебной цепочкой `_chain`. `cycle_core` забирает её,
запускает `core_worker.php` в отдельном PHP-процессе и загружает
`modules/<module>/<module>.class.php`.

Контракт модуля:

```php
public function propertySetHandle($object, $property, $value)
```

Возвращаемое значение не обязательно; `false` означает временную ошибку и
повтор операции. Не указывайте `: void`, если обработчик может вернуть `false`.

Требования:

- обработчик должен быть идемпотентным: при потере подтверждения операция
  повторится;
- возврат `false`, исключение или таймаут — временная ошибка, привязка
  сохраняется, операция повторяется (до 3 попыток с задержкой 5/10 секунд,
  затем `operations_failed`);
- обработчик не должен рассчитывать на HTTP-сессию или `$_SERVER` web-запроса;
- если файл модуля отсутствует, но модуль зарегистрирован
  (`cms/modules_installed/<module>.installed` или `project_modules`), привязка
  **не удаляется** — это считается деплоем/сбоем установки;
- если файла нет и модуль не зарегистрирован, после трёх попыток привязка
  вычищается как устаревшая;
- если класс загрузился, но метода `propertySetHandle` нет, привязка также
  считается устаревшей.

## 4. Хранение и владение привязкой

`pvalues.LINKED_MODULES` — список имён модулей через запятую. Формат сохранён
для совместимости со старыми модулями, бэкапами и страницей объекта.

Новый код:

```php
use MajorDoMo\Core\Core;

Core::bindings()->attach('Lamp', 'status', 'mqtt');
Core::bindings()->detach('Lamp', 'status', 'mqtt');
Core::bindings()->detachIfUnused('mqtt', 'Lamp', 'status', 'mqtt');
Core::bindings()->modules('Lamp', 'status'); // ['mqtt', 'scripts']
```

Правила:

- `attach/detach` меняют **только** `LINKED_MODULES` compare-and-swap-запросом.
  `VALUE`, `UPDATED`, `SOURCE` не перезаписываются, параллельно добавленный
  подписчик не теряется. Если строки значения ещё нет, `attach` создаёт её с
  пустым `VALUE`; `detach` ничего не создаёт и возвращает `false`, если строки
  или подписки нет. `attach` возвращает ID строки значения (`0`, если объект
  или свойство не найдены).
- Токены нормализуются: пробелы и дубликаты удаляются при ближайшей записи.
- Имя модуля проверяется тем же шаблоном, что и worker:
  `^[A-Za-z_][A-Za-z0-9_]*$`.
- `detachIfUnused($table, …)` принимает только идентификатор таблицы
  (`^[A-Za-z_][A-Za-z0-9_]*$`) и снимает подписку, только если в этой таблице
  больше нет строки с такой парой `LINKED_OBJECT/LINKED_PROPERTY`.
- Владелец привязки — запись модуля (`mqtt`, `scripts`, `zigbee_bindings`, …).
  Сначала удалите/сохраните запись, затем вызывайте `detachIfUnused()`. Иначе
  проверка увидит текущую запись и оставит «вечную» подписку.
- `LINKED_MODULES` — `varchar(255)`. Переполнение отклоняется с понятной
  ошибкой; молчаливое обрезание запрещено.

Старые функции остаются фасадами:

```php
addLinkedProperty($object, $property, $module);            // → attach()
removeLinkedProperty($object, $property, $module);         // → detach()
removeLinkedPropertyIfNotUsed($table, $object, $property, $module); // → detachIfUnused()
```

## 5. Почему старые привязки «слетали»

Исправленные причины:

1. `addLinkedProperty()` читал всю строку `pvalues`, менял `LINKED_MODULES` и
   писал строку целиком. Параллельная запись значения откатывалась к старому
   `VALUE`, а параллельно добавленный подписчик терялся.
2. `removeLinkedPropertyIfNotUsed()` вызывался до сохранения записи модуля.
   Проверка видела саму редактируемую запись и не снимала старую подписку.
3. `scripts_edit.inc.php` снимал подписку по **новым** вычисленным значениям,
   а не по старым, и до `UPDATE`/`INSERT`.
4. `mqtt_edit.inc.php` снимал `mqtt` безусловно. Если два топика MQTT смотрели
   на одно свойство, редактирование одного отключало второй.
5. Подписка могла быть записана в устаревшую строку `pvalues` с тем же
   `PROPERTY_NAME`, но другим `PROPERTY_ID` (переопределённое свойство класса).
6. `LIKE` в обработчиках MQTT/scripts считал `_` и `%` в имени объекта
   шаблоном и мог вызвать чужой топик/сценарий.
7. Удаление сценария не снимало его подписку; удаление MQTT-топика снимало
   корректно, но редактирование — нет.
8. Удаление файла модуля во время деплоя трактовалось как «модуль удалён» и
   вычищало рабочие привязки после трёх коротких повторов.
9. `scripts/startup_maintenance.php` при каждом старте `cycle_main` удалял
   объектное свойство, если в классе появлялось свойство с тем же именем.
   Вместе с ним удалялись `LINKED_MODULES` и история; значение класса могло
   остаться старым. Теперь строка значения переносится/сливается: побеждает
   более новое значение, подписки объединяются, история переезжает на активную
   строку (`Migrations::mergeRows()`), а `PROPERTY_NAME` обновляется точечно.
10. Переименование объекта обновляло только `objects.TITLE`. В `mqtt`,
    `scripts`, `zigbee_bindings`, `events_params` и других таблицах оставался
    `LINKED_OBJECT` со старым именем: подписка в `LINKED_MODULES` была, а
    `propertySetHandle()` искал старое имя и молча ничего не делал. Теперь
    `Objects::renameReferences()` обновляет все таблицы с `LINKED_OBJECT` и
    метки `pvalues.PROPERTY_NAME`.
11. Переименование свойства аналогично оставляло старый `LINKED_PROPERTY` в
    модулях. `Properties::renameReferences()` обновляет `LINKED_PROPERTY` только
    для объектов, у которых реально есть строка значения этого свойства, и
    синхронизирует `PROPERTY_NAME`; чужие классы с тем же именем не задеваются.

## 6. Проверка перед продакшеном

```bash
php tests/property_onchange_smoke.php
php tests/stale_module_bindings_smoke.php
```

Проверить в БД:

```sql
-- Подписчики, которых нет в каталоге модулей
SELECT p.ID, p.PROPERTY_NAME, p.LINKED_MODULES
FROM pvalues p
WHERE p.LINKED_MODULES <> '';

-- Дубли строк значения (должно быть пусто после миграции)
SELECT PROPERTY_ID, OBJECT_ID, COUNT(*) AS CNT
FROM pvalues GROUP BY PROPERTY_ID, OBJECT_ID HAVING CNT > 1;

-- Объектное свойство, которое дублирует свойство класса (старт цикла
-- переносит его в класс и объединяет привязки, а не удаляет).
SELECT op.ID, o.TITLE AS OBJECT_TITLE, op.TITLE AS PROPERTY_TITLE
FROM properties op
JOIN objects o ON o.ID=op.OBJECT_ID
JOIN properties cp ON cp.TITLE=op.TITLE AND cp.OBJECT_ID=0 AND cp.CLASS_ID=o.CLASS_ID
WHERE op.OBJECT_ID<>0;

-- Неразобранные фоновые операции и постоянные ошибки
SELECT COUNT(*) FROM operations_queue;
SELECT COUNT(*) FROM operations_failed;
```

Эксплуатационные условия:

- `cycle_core` запущен и живой: без него очередь `modulepropertyset` не
  разбирается;
- очередь операции живёт 1 час (`EXPIRE`): после длительного простоя
  уведомления, не доставленные за это время, пропадают; значение свойства при
  этом остаётся корректным;
- ошибки доставки видны в `operations_failed` (SQL) или
  `queue:failed:core_runtime` (Redis), а также в журнале `property_delivery`
  (дедуплицировано, не по одной записи на каждое значение);
- `ErrorReporter` подавляет повторы одного и того же сбоя на 5 минут; при
  падении БД это не превращается в поток ошибок;
- при обновлении, которое заменяет файлы модулей, подписки на зарегистрированные
  модули не удаляются;
- после восстановления из бэкапа проверьте, что `LINKED_MODULES` ссылается на
  реально установленные модули.

## 7. Известные ограничения

- `LINKED_MODULES` — `varchar(255)` для **имён модулей-подписчиков**, без
  отдельной таблицы подписок. Значение свойства хранится в `pvalues.VALUE`
  (`text`) и этим лимитом не ограничено. При переполнении списка будет
  понятная ошибка, а не молчаливое обрезание.
- Уведомление модуля — at-least-once. Обработчик обязан быть идемпотентным.
- Если постановка уведомления в очередь не удалась, значение свойства уже
  сохранено; ошибка попадает в `ErrorReporter` (код `property_delivery`) один
  раз за окно. Строгий режим включается `PROPERTY_DELIVERY_STRICT=true`.
- Прямое эхо модуля автоматически подавляется, а повтор свойства в цепочке
  обрывает дальнейшие уведомления. Это защита от `A → script → A` и
  `A → script1 → B → script2 → A`; при повторном срабатывании пишется
  предупреждение `property_chain` с причиной (повтор свойства или лимит
  `PropertyChain::MAX_LENGTH`), последними шагами цепочки и подсказкой, что
  делать.
- Очередь операции живёт 1 час. Долгий простой `cycle_core` означает потерю
  уведомлений, но не значения свойства.
- В web-запросе `ONCHANGE` теперь тоже асинхронный: страница не ждёт метод.
  Если нужен результат сразу после изменения, проверяйте свойство/историю после
  обработки очереди, а не в том же рендере.

## 8. Как добавить привязку в новый модуль

1. Добавьте в таблицу модуля поля `LINKED_OBJECT` и `LINKED_PROPERTY`
   (по необходимости `LINKED_METHOD`).
2. При сохранении записи: сначала `UPDATE/INSERT`, затем
   `addLinkedProperty($object, $property, $module)` — или сразу
   `Core::bindings()->attach($object, $property, 'my_module')`.
3. При удалении/смене привязки: сначала удалите/сохраните запись, затем
   `removeLinkedPropertyIfNotUsed('<table>', $oldObject, $oldProperty, $module)`
   (`Core::bindings()->detachIfUnused(...)`). Иначе проверка увидит текущую
   запись и оставит подписку.
4. Реализуйте `propertySetHandle($object, $property, $value)`; не полагайтесь на
   web-сессию и делайте обработчик идемпотентным.
5. Не добавляйте модуль в `LINKED_MODULES` вручную и не пишите `pvalues`
   целиком.

Минимальный шаблон сохранения и снятия привязки:

```php
use MajorDoMo\Core\Core;

// 1. Сохранили/обновили запись модуля (UPDATE/INSERT).
// 2. Подписались на изменение свойства.
Core::bindings()->attach($object, $property, 'my_module');

// При удалении или смене привязки:
// 1. Удалили/сохранили запись модуля.
// 2. Сняли подписку, только если пара OBJECT/PROPERTY больше не используется.
// Первый аргумент — таблица модуля-владельца, последний — имя модуля.
Core::bindings()->detachIfUnused('my_module', $oldObject, $oldProperty, 'my_module');
```

Старые имена `addLinkedProperty()`, `removeLinkedProperty()` и
`removeLinkedPropertyIfNotUsed()` остаются фасадами над этими же методами.
