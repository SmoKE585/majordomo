# Надёжная доставка заданий ядра

## Сохранение и исполнение

`core_runtime_queue` — долговечный журнал незавершённых и неудачных заданий.
При включённом `USE_REDIS` исполнители получают задания через Redis и
`LaneEventQueue`; SQL сохраняет их до подтверждения. Без Redis те же записи
резервируются в SQL. Входящая и исходящая очереди MQTT этим изменением не заменяются.

Запись свойства держит `PropertyLock` до завершения последовательности:

1. Валидация и чтение предыдущего значения.
2. Транзакция: значение, аудит, история, уведомления модулей и `ONCHANGE`.
3. `COMMIT`, инвалидация кеша и сообщение WebSocket.
4. Снятие блокировки свойства.

Ошибка сохранения любого задания откатывает всю запись. Успех `sg()` означает,
что значение и задания зафиксированы, но не подтверждает выполнение устройства.
Настройка `PROPERTY_DELIVERY_STRICT` сохранена для старых конфигураций; запись
новых заданий всегда строгая. Публичные сигнатуры и результаты `sg()` не меняются.

Вложенная запись использует точку сохранения. Во внешней транзакции общий кеш
не читается и не заполняется незавершёнными значениями; уведомление WebSocket и
инвалидация ждут её `COMMIT`. Запросы ядра получают исключения драйвера,
старые глобальные SQL-функции сохраняют свой интерфейс.

## Передача в Redis и восстановление

Передача идёт по порядку SQL ID. Redis принимает стабильный ID один раз,
поэтому обрыв после добавления в Redis, но до отметки в SQL, не создаёт дубль.
После потери Redis меняется ключ поколения: все незавершённые задания снова
передаются из SQL. Действующая SQL-аренда защищает ещё работающий процесс от
параллельного повторного запуска. Запоздалый токен не может подтвердить новую аренду.

При успехе сначала удаляется запись SQL, затем подтверждается элемент Redis.
Обрыв между этими действиями оставляет элемент Redis, который удаляется при
следующем резервировании без повторного выполнения обработчика.

Порядок сохраняется внутри объекта. Сценарии, API и подписки работают в
эксклюзивной полосе `serial`. Отложенный повтор блокирует следующие задания
своего объекта, но позволяет обрабатывать другие объекты. При `CORE_WORKERS=1`
все задания идут последовательно. Число воркеров не зависит от наличия Redis.

## Ошибки и остановки

- Исключение, явный `false`, таймаут и выход без результата не подтверждают успех.
- Не больше трёх попыток, включая аварийное завершение контроллера без ответа.
  Между обычными повторами есть задержка; последняя причина сохраняется в SQL.
- После исчерпания попыток задание получает `STATUS=failed`, а объект продолжает
  обработку следующих событий. Бесконечных повторов устройству нет.
- Срок ожидания остаётся одним часом. Просроченное задание становится видимым
  отказом, а не исчезает. Активный обработчик не удаляется из-за срока ожидания.
- Пользовательский код выполняется отдельным процессом. На Linux с `pcntl`
  процесс получает собственный дедлайн на случай гибели контроллера. Штатная
  остановка контроллера завершает активную группу процессов и подготовленного ребёнка.
- Контроллеры обновляют файловый heartbeat, независимый от MySQL и Redis.
  Супервизор перезапускает контроллер без прогресса после таймаута обработки с запасом.
- `EventBus::drain()` атомарно передаёт подписки в долговечную очередь и не
  исполняет код модуля в супервизоре. Ошибки фонового подписчика передаются
  механизму повторов; `system_events.PROCESSED=1` означает передачу задания.

Выполнение остаётся с возможными повторами: если устройство уже выполнило команду,
а процесс погиб до подтверждения SQL, повтор допустим. Обработчики должны быть
идемпотентными. Общей транзакции с физическим устройством нет. Частичная потеря
отдельных ключей Redis из-за вытеснения не равна полному восстановлению сервера:
для рабочих очередей по-прежнему требуется `noeviction` и штатное persistence.

## Обновление и диагностика

Штатная миграция создаёт таблицу и переносит старые SQL/Redis-задания при
остановленных циклах. Исходные ключи удаляются после сохранения снимка в SQL;
`SOURCE_KEY` защищает повтор миграции после обрыва. Старый Redis-журнал отказов
сохраняется. Миграции выполняются по порядку имён файлов, независимо от
алфавитного порядка их текстовых меток версии. Рабочая запись свойств DDL не запускает.

```bash
php majordomo queue:status
php majordomo queue:status --failed --limit=20 --json
```

Команда только читает состояние и причины отказов, не повторяет команды устройствам.
Для расследования служат `core_runtime_queue.LAST_ERROR`, журнал `property_delivery`
и журналы контроллеров. Автоматическое переключение на другую очередь при отказе
настроенного Redis не выполняется: зафиксированные задания ждут восстановления.

Проверки: `tests/runtime_durability_smoke.php` (обрывы настоящих PHP-процессов,
SQLite), `tests/core_lanes_smoke.php` (настоящий изолированный Redis),
`tests/core_runtime_smoke.php` (одноразовые MariaDB/Redis, конкурентные писатели),
`tests/process_runner_smoke.php` (Linux-процессы), `tests/queue_status_smoke.php`.
