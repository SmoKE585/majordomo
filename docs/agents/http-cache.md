# HTTP-кэш с валидацией

## Зачем

Раньше `getURL()` складывал ответы в `cms/cached/urls/<url>.html` и проверял
только время файла. Это давало три проблемы:

- неудачный запрос (таймаут, пустой ответ) кэшировался и подменял ленту
  обновлений пустотой на весь TTL;
- после обновления системы старый ответ ещё жил в кэше, и UI показывал
  «есть обновление» поверх только что установленной версии;
- кэш не использовал серверную валидацию, поэтому каждый TTL означал полную
  повторную загрузку.

Теперь ответы хранит `MajorDoMo\Core\Http\HttpCache`, а `getURL()` умеет
условные запросы. Публичная сигнатура `getURL()` не изменилась.

## Хранилище

| Условие | Где лежит запись |
| --- | --- |
| `USE_REDIS` включён и расширение Redis доступно | Redis-хэш `http:<sha256>` |
| Redis выключен или недоступен | `cms/cached/http/<sha256>.json` |

Переключение автоматическое. Если Redis недоступен, запись уходит в файл; если
потом Redis заработает, следующая запись ляжет в Redis, а файловая копия будет
удалена. Битый JSON считается промахом и удаляется.

Запись содержит тело, `etag`, `last_modified` и `stored_at`. Тело в файловом
варианте хранится в base64: ответ не обязан быть в UTF-8.

## Ключ

`HttpCache::key($url, $method = 'GET', $payload = '')` — `sha256` от метода,
URL и тела запроса. URL без нормализации: разные строки — разные записи.
POST получает отдельный ключ, поэтому одинаковый адрес с разными данными не
отдаёт чужой ответ.

`getURLCacheFile($url)` возвращает путь файловой копии GET-запроса; он нужен
для диагностики и ручной очистки. `clearURLCache($url)` удаляет запись и из
Redis, и из файла. Общая очистка `clearCache()` (в том числе на каждый POST
админки) вызывает `HttpCache::clear()` и удаляет весь HTTP-кэш.

## Валидация

`getURL($url, $cache)`:

1. читает запись;
2. если `time() - stored_at <= $cache`, возвращает тело без сети;
3. иначе добавляет `If-None-Match` и `If-Modified-Since` и делает запрос;
4. на `304 Not Modified` возвращает сохранённое тело и продлевает запись;
5. на `2xx/3xx` с непустым телом сохраняет ответ и валидаторы;
6. на сетевую ошибку или `4xx/5xx` ничего не пишет.

Заголовки ответа читаются через `CURLOPT_HEADERFUNCTION`. Если вызывающий код
передал свой `CURLOPT_HTTPHEADER` в `$curl_options`, условные заголовки
объединяются с ним, а не затираются.

`$background = true` не читает и не пишет кэш: фоновый вызов не должен
возвращать старый ответ вместо отправки запроса.

## Сброс

После успешной установки системного обновления `saverestore` вызывает
`clearURLCache()` для ленты обновлений. Без этого закэшированная лента до
30 минут утверждает, что последний коммит — прежний, и интерфейс показывает
ложное «есть обновление».

TTL ленты обновлений — `saverestore::UPDATE_FEED_TTL` (30 минут). Проверка по
кнопке «Проверить обновление» и перед установкой не доверяет старому кэшу
(TTL=1 секунда), но всё равно обновляет его для следующих плановых проверок.

## Проверки

- `php tests/http_cache_smoke.php` — файловое хранилище, TTL, 304, обновление
  тела, отказ от кэширования ошибок, сброс;
- `php tests/saverestore_update_version_smoke.php` — разбор ленты, ссылка на
  архив коммита, отпечаток архива и запись версии без БД и сети.
